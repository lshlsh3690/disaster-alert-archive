# 이벤트 클러스터링 평가 파이프라인 — RAG 평가 단계와의 대응

RAG 평가는 보통 검색(Retrieval) → 생성(Generation) → 엔드투엔드로 나눠 병목을 찾는다. 이벤트 클러스터링은 RAG가 아니지만 같은 구조로 쪼개서 평가하면 오류 원인을 단계별로 분리할 수 있다. 이 문서는 그 대응 관계, 단계별 평가 방법, 현재 도구의 상태를 기록한다.

## 1. 단계 대응

| RAG 단계 | 클러스터링에서의 의미 | 입력 → 출력 |
|---|---|---|
| 검색 (Retrieval) | 새 재난문자와 **연관된 문자/이벤트를 후보로 선정** | 새 문자 → 후보 이벤트 (최대 3개) |
| 생성 (Generation) | 후보와 **묶을지 말지를 결정**. 묶으면 병합, 아니면 신규 이벤트 | 새 문자 + 후보 → 병합 / 신규 |
| 엔드투엔드 | 최종 결과로 **여러 재난문자가 묶인 이벤트**가 나오는 것 | 문자 스트림 → 이벤트 집합 |

### 검토 의견: 이 대응은 맞고, 세 가지를 보정해서 기록한다

1. **검색을 건너뛰는 경로가 있다.** 인물(실종), 태풍, 지역앵커 유형(산불·산사태·홍수), 에피소드형(폭염·한파·대설·강풍·가축질병), 안내성(`기타` 물놀이)은 후보를 검색하지 않고 "유형+시군구" 같은 규칙 키로 곧바로 이벤트를 정한다. 이 경로에서는 검색과 판정이 하나로 합쳐져 있어서 검색 실패/판정 실패로 나누어 볼 수 없다. 단계별 분해는 **임베딩 경로(그 외 유형)에서만** 의미가 있다.
2. **"생성 단계"는 텍스트 생성이 아니라 이진 판정이다.** 출력이 병합/신규 둘 중 하나이고 대부분 결정적 규칙(거리 임계값, 가드)이다. 생성 모델에 해당하는 것은 사고성 유형의 borderline 건에서 호출하는 LLM 폴백뿐이다.
3. **엔드투엔드는 쌍 지표만으로 충분하지 않다.** 쌍 단위 정밀도·재현율은 최종 이벤트를 쌍으로 풀어서 본 대리 지표다. 이벤트의 모양(여러 시군구·긴 기간에 걸쳐 이어 붙은 것, 한 사건이 여러 이벤트로 쪼개진 것)은 쌍 라벨에 없으면 보이지 않는다(5절 사례).

## 2. 현재 구현과 평가 지표

### 2.1 검색 단계
- **구현**: `DisasterEventRepository.findTopCandidates` — 같은 시군구(앞 5자리) footprint 교집합, 마지막 알림이 윈도우(168h) 안, 광역·안내 이벤트 제외, 이벤트별 최소 코사인 거리 오름차순 상위 3개. 사고성 유형은 `findTopAdjacentCandidates`로 `region_adjacency` 이웃 시군구의 이벤트도 추가 조회한다(윈도우 48h, 후보 이벤트 첫 알림 72h 이내 등 가드 포함).
- **지표**: 후보 재현율 — 정답 이벤트가 그 시점 후보 3개 안에 있었는가. 못 들어간 쌍을 **검색 실패(RETRIEVAL_MISS)**로 센다. 쌍 분리도(AUC·margin)와 임계값 스윕으로 거리 분포도 본다.
- **한계**: 평가는 현재 이벤트 상태에서 "그 시점의 후보"를 근사한다(`as-of` 근사).

### 2.2 판정 단계
- **구현**: `EventClusteringService` — 거리 임계값(기본 0.15, 완화 유형 0.35) → 사고성 유형의 인접 시군구 임계값 병합 → borderline 사고성 건의 LLM 폴백(`tryLlmFallback`) → 신규 이벤트. 병합 전 가드(`allowsAccidentMerge`: 사고성 유형, 화재 마지막 알림 72h, `withinAdjacentEventAge`: 이벤트 첫 알림 72h).
- **지표**: 정답 이벤트가 후보에 있었는데 합치지 않은 쌍을 **판정 실패(DECISION_MISS)**, 다른 사건인데 합친 쌍을 **과병합(OVER_MERGE)**으로 센다.
- **한계**: 평가 실행에서는 LLM 폴백을 꺼 둔다(비용). 따라서 판정 실패 수치는 운영보다 보수적이다.

### 2.3 엔드투엔드
- **구현된 것**: 최종 이벤트 배정을 쌍으로 풀어 층(일반 60% / 경계 20% / 함정 20%)별 tp·fp·fn·tn, 정밀도·재현율·F1 (`PairwiseEvaluator`, `EventEvaluationService`).
- **수동으로 점검한 것**: 이벤트가 걸친 시군구 수 분포, 이벤트 기간, 광역 이벤트 수, 단발 이벤트 수 — SQL로 직접 확인했고 자동화하지 않았다.
- **없는 것**: 이벤트 순도(한 이벤트 안에 서로 다른 사건이 섞였는가), 분절도(한 사건이 몇 개 이벤트로 쪼개졌는가)의 자동 지표.

## 3. 오류와 단계의 대응

| 증상 | 단계 | 분류 |
|---|---|---|
| 정답 이벤트가 후보 3개에 없음 | 검색 | 검색 실패 |
| 후보에 있는데 합치지 않음 | 판정 | 판정 실패 |
| 다른 사건을 합침 | 판정 (또는 검색이 엉뚱한 후보를 올림) | 과병합 |
| 이웃 시군구를 따라 연쇄로 이어 붙어 거대한 이벤트가 됨 | **엔드투엔드** (검색·판정 각각은 정상) | 쌍 지표로 안 잡힘 |
| 단발 이벤트가 불필요하게 늘어남 | 엔드투엔드 | 쌍 지표로 안 잡힘 |

판정 기준(rubric)은 `backend/evaluation/datasets/cluster-eval-2026-10.rubric.md`에 있다. 같은 에피소드와 되풀이 안내는 같은 사건, 별개의 사고와 서로 다른 지역에서 병렬로 안내되는 같은 기상 상황은 다른 사건으로 본다.

## 4. 평가 데이터
- 라벨 150문항: `backend/evaluation/datasets/cluster-eval-2026-10.csv`(문항), `cluster-eval-2026-10.labels.json`(라벨), `.rubric.md`(기준). DB 테이블 `evaluation_label`(V130)에 "지우고 다시 넣기"로 적재한다.
- 한계: 라벨러 1명, 부정 예시 38개, 시스템이 틀리기 쉬운 쌍 위주의 층화 표본이라 실제 트래픽의 품질을 대표하지 않는다. 개발용/최종용 분리가 없다.

## 6. LLM-as-a-Judge의 위치

- **평가자로서 쓴다**: 사람 라벨을 대신해 쌍 단위 판정을 대량으로 만들어 정밀도·재현율을 더 큰 표본에서 추정한다(판정 단계와 종단 지표의 측정 규모를 늘림). 운영 코드의 LLM 폴백과 별개이며, 판사 모델은 운영 모델(`gpt-4o-mini`)과 다른 `gpt-4o`를 쓴다.
- **먼저 검증한다**: 사람이 라벨한 쌍으로 일치율·kappa를 재서 통과해야 이후 단계로 간다.
- **비용을 통제한다**: 실행 전 예상 비용 출력, 상한 초과 시 시작하지 않음, 실행 중 누적 비용이 상한이면 중단, 결과를 DB에 캐시해 같은 쌍을 다시 과금하지 않음.
- **이벤트 순도 판정은 후속**이다. 단 위 3절의 연쇄 병합처럼 "의미는 같은 안내문인데 지역·기간이 퍼진" 문제는 의미 판정이 아니라 시군구 수·기간 같은 결정적 지표로 잡는 편이 정확하다.
- 별도 항목으로 **운영 LLM 폴백을 켠 재측정**이 있다. 평가자가 아니라 시스템 구성요소를 켜는 것이다.

## 7. 남은 과제
1. 검색: 후보 top-3 안에 못 오른 쌍 7건 — 키워드 하이브리드 검색, 후보 수 확대 검토.
2. 판정: LLM 폴백을 켠 상태의 지표, 임계값 재조정.
3. 엔드투엔드: 이벤트 순도·분절도·시군구 수·기간·단발 비율의 자동 지표.
4. 데이터: 무작위 표본, 어려운 부정 예시, 개발/최종 분리, 두 번째 라벨러(또는 판사 LLM).
5. 튜닝 후 단계별 전후 비교를 최종 보고서로 정리(중간 리포트는 저장소에 올리지 않기로 함).
