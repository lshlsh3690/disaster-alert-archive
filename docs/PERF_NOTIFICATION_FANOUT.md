## 2. 개선 전 구조와 원인 분리 규명

`triggerNotification()`은 회원 1만 명 순회를 `@Transactional` 메서드 하나로 통째로
감싼다. 회원마다 `sendToMembers()`에서 `NotificationPreference`/`FcmToken`을 개별
조회하는 **N+1 패턴**이 있었고, 이와 별개로 **세션(영속성 컨텍스트) 누적** 문제도
있었다 — 트랜잭션이 끝날 때까지 Hibernate가 관리 엔티티를 계속 쌓아두고, 컨텍스트가
커질수록 매 쿼리 전 더티체킹 비용이 늘어난다.

세션 누적의 근거: `EXPLAIN (ANALYZE, BUFFERS)`로 확인한 DB 쿼리 자체는
0.04~0.05ms인데, 애플리케이션 레벨 소요시간은 루프 진행에 따라 **회원당 31ms →
93ms로 약 3배 증가**했다 — 순수 쿼리 비용이 아니라 세션이 커질수록 앱 레벨에서
따로 비용이 붙는다는 뜻이다.

## 3. 1단계 → 2단계 순차 적용 결과

| 단계 | 조치 | 소요시간 | 이전 단계 대비 |
|---|---|---|---|
| 0 (원본) | 없음 | 1,073,301ms (17분 53초) | — |
| 1단계 | flush/clear 주기 500 적용 (N+1 쿼리는 그대로 유지) | 132,581ms (2분 12.6초) | **약 8.1배** |
| 2단계 | 1단계 + 벌크 조회(JPQL 생성자 프로젝션)로 N+1 제거 | 21,562ms (21.6초) | **추가 약 6.15배** |

**1단계의 8.1배는 세션 누적 제거의 단독 기여가 아니다.** 1단계의 before(1,073,301ms)에는
세션 누적과 N+1 두 원인이 함께 포함되어 있고, N+1이 아직 남아있는 상태에서 세션 문제만
고친 결과가 8.1배다. 각 배수는 항상 "그 단계가 시작된 시점의 소요시간 대비"로 읽어야
한다.

## 4. 왜 "49.8배"를 쓰지 않는가

`1,073,301 / 21,562 ≈ 49.8`은 산술적으로는 맞는 값이다. 하지만 이는 세션 누적 제거와
N+1 제거라는 **서로 다른 두 원인의 기여를 곱한 값**이라, 마치 하나의 개선이 49.8배를
낸 것처럼 읽힌다. 그래서 이 문서에서는 이 값을 단독 수치로 쓰지 않고, 3절의 두 단계
표로만 서술한다.

## 6. 적용 순서를 바꿨다면? (정성적 서술만, 실측 없음)

이번 라운드는 세션 관리(flush/clear)를 먼저 적용하고 N+1 제거를 나중에 적용했다. 만약
반대 순서로 적용했다면 — N+1 제거를 먼저, 세션 관리를 나중에 — **N+1 제거 단계가 더
큰 배수를, 세션 관리 단계가 더 작은 배수를 보였을 것**이다. 어느 조치를 먼저 적용하든
그 조치의 before에는 아직 처리되지 않은 나머지 원인의 비용이 섞여 있어서, 순서상
먼저 오는 단계가 항상 더 큰 배수를 갖는 구조이기 때문이다.

**이 역순 시나리오는 실측하지 않았다.** 방향성("더 컸을 것/더 작았을 것")만 서술하며,
구체적인 배수나 소요시간은 지어내지 않는다.

## 7. 최종 결과 (2026-10-03 개정 — 분류 기준 재정리)

개선을 세 가지로 구분한다.

| 구분 | 내용 | 성과 수치로 쓰는가 |
|---|---|---|
| 선행 버그 수정 | 세션(영속성 컨텍스트) 누적 — `@Transactional` 메서드 하나가 회원 1만 명 순회 전체를 감싸고 flush/clear가 없던 **구현 실수**. 1,073초 → 133초 | 아니오 (처음부터 잘못 짠 코드를 고친 것) |
| 문제 해결 | N+1 제거 — 회원마다 알림설정·FCM 토큰을 개별 조회(1만 명 기준 2만 회)하던 것을 일괄 조회 2회로 | 배수로는 쓰지 않는다 |
| 성능 개선 | PK 전략을 SEQUENCE로 바꿔 JDBC 배치 INSERT 활성화 (8절) | 예 — 같은 조건에서 잰 실측치로만 |

**N+1을 "6배"로 내세우지 않는 이유.** 133초 → 22초(약 6.15배)는 회원 1만 명, 로컬 DB라는
조건에서 나온 측정값이다. N+1은 쿼리 횟수가 회원 수에 비례해 늘어나던 구조(2N회 → 2회)를
없앤 것이라, 규모가 달라지면 배수도 달라진다(10만 명이면 더 클 수 있다). 규모에 따라 변하는
값이라 고정 배수로 제시하면 오해를 낳는다. 그래서 **쿼리 횟수라는 구조적 사실로 서술**하고,
6.15배는 "1만 명 조건에서 잰 참고 수치"로만 남긴다.

(2026-10-01 판의 이 절은 "6.15배(133초 → 22초)를 유일한 성능 개선 수치"로 정했다. 위 분류로
대체한다 — N+1은 문제 해결로, 성능 개선은 8절의 배치 INSERT로 옮겼다. 그 이전 판은
"1,073초 → 22초, 두 개선의 누적 결과"였고, 버그 수정분까지 성과에 넣는 프레이밍이라 폐기했다.)

## 8. 후속 개선: SEQUENCE + 배치 INSERT (2026-10-03)

### 8.1 원인

`UserNotificationLog`의 PK가 `GenerationType.IDENTITY`라 Hibernate가 JDBC 배치를 꺼서, 회원마다
INSERT가 DB 왕복 1회씩이었다. `application.yml`에는 `hibernate.jdbc.batch_size: 500`,
`order_inserts: true`가 이미 있었지만 이 경로에서는 작동하지 않았다 — **"설정이 존재한다"와
"설정이 작동한다"는 다르다.**

### 8.2 변경

- `UserNotificationLog`: `SEQUENCE` + `allocationSize = 500`. 기존 BIGSERIAL 시퀀스
  `user_notification_log_id_seq`를 그대로 재사용한다(새 시퀀스를 만들지 않음).
- `V120`: 그 시퀀스를 `INCREMENT BY 500`으로 변경. Hibernate의 `allocationSize`와 맞춰야
  `ddl-auto: validate`가 통과한다. 시퀀스 현재값이 기존 최대 id 이상이라 `setval`이 필요 없고,
  옛 코드(IDENTITY)로 롤백해도 같은 시퀀스를 써서 id가 충돌하지 않는다(500씩 건너뛸 뿐).
- `FLUSH_INTERVAL = 500`의 flush가 곧 JDBC 배치 경계가 된다. `batch_size`, `allocationSize`,
  `FLUSH_INTERVAL`을 의도적으로 같은 500으로 맞췄다.
- INSERT가 flush 시점으로 미뤄지면서 생기는 오류 처리 변화는 8.6절.

### 8.3 측정 조건

- 로컬 Postgres(docker), `fanout-trigger` 프로필, `--fcm.dry-run=true`로 **FCM 호출을 제외한 DB
  구간만** 측정. 채택 지표는 로그의 "회원 팬아웃 완료 ... time=Xms".
- 같은 DB, 같은 시드 회원(전원 같은 핫 지역 관심지역)을 대상으로 변경 전·후를 측정했다.
  변경 전 코드는 별도 worktree(커밋 `4833c8c`)에서 같은 조건으로 돌렸다.
- 5만 명은 시드 스크립트를 반복 실행해 핫 지역 회원을 5만 명으로 늘린 뒤 측정했다.

### 8.4 결과

| 대상 | 변경 전 (IDENTITY) | 변경 후 (SEQUENCE + 배치) | 배수 |
|---|---|---|---|
| 1만 명 | 21.5, 22.1, 21.8초 (중앙값 21.8초) | 1.04, 1.06, 1.02, 1.05, 1.06초 + **5.68초(이상치 1회)** (중앙값 1.05초) | 약 21배 |
| 5만 명 | 148.1, 119.3초 (중앙값 133.7초) | 4.43, 4.50, 4.57, 4.59, 4.61초 (중앙값 4.57초) | 약 29배 (26~33배) |

- 회원당 시간: 변경 전 2.2ms(1만 명) → 2.4~3.0ms(5만 명), 변경 후 0.105ms → 0.091ms.
- 규모가 5배가 될 때 걸리는 시간은 변경 전 5.5~6.8배, 변경 후 4.4배로 늘었다.
- **배수는 고정된 성질이 아니다.** 1만 명 약 21배, 5만 명 약 29배로 규모에 따라 달라졌다. 하나의
  배수로 일반화하지 않고 규모별 실측치를 함께 쓴다.
- 변경 후 마지막 코드(flush 실패 처리 포함)로 5만 명을 다시 재서 정상 경로 성능이 같음을 확인했다
  (4.43, 4.61초).
- 발송 실패 0건, 변경 전·후 모두 `user_notification_log`에 대상 인원만큼 행이 저장됨을 확인했다.

### 8.5 한계 (그대로 기록한다)

- **FCM 호출은 측정에 없다.** 이 수치는 "푸시 발송 소요시간"이 아니라 알림 팬아웃의 DB 구간이다.
  실제로는 회원마다 FCM 호출이 순차로 붙으므로 종단 소요시간은 훨씬 길 수 있고, 얼마나 되는지는
  측정하지 않았다.
- 변경 전 5만 명은 2회뿐이고 두 값의 차이가 약 20%다. 측정 중 로그 테이블이 커진 영향도 분리하지
  못했다.
- 변경 후 1만 명에서 5.68초가 한 번 나왔다. DB 백그라운드 작업(체크포인트 등) 때문으로 추정하지만
  확인하지 않았다.
- `reWriteBatchedInserts=true`(JDBC URL 옵션)는 4.5~5.1초로 더 느렸지만, 옵션 없는 상태에서도
  5.68초 이상치가 나와 옵션 탓인지 구분하지 못했다. 이득이 확인되지 않아 **채택하지 않았다.**
- 일괄 조회의 `IN` 목록은 5만 건까지 정상 동작을 확인했다. 10만 건 이상은 확인하지 않았다.
- 로컬 DB 한 대, 합성 데이터이며, 회원당 호출 추적 로그가 포함된 상태의 측정이다.

### 8.6 트레이드오프

INSERT가 flush 시점(500건마다)으로 미뤄져, 이력 저장 실패가 `sendToMember`의 try/catch 밖에서
드러난다.

- flush 실패는 `AlertNotificationService`에서 잡아 error 로그만 남기고 **발송은 계속한다**.
  게스트 토큰 조회를 회원 팬아웃 앞으로 옮겨, 실패 후 조회가 안 돼 게스트 FCM이 누락되는 일을
  막았다.
- 다만 flush가 실패하면 Postgres 트랜잭션이 aborted 되어 같은 `@Transactional` 안의 이후 flush도
  실패하고 커밋 시 롤백되므로, **이미 FCM이 나간 회원의 이력이 일부 또는 전부 사라질 수 있다.**
  발송 지속을 우선한 의도적 선택이다.
- flush 실패 로그는 한 번의 팬아웃에서 첫 실패만 error, 이후는 warn으로 남긴다. 시퀀스 블록이
  소진돼 `nextval`이 필요해지는 시점부터는 `save()`도 실패해 회원별 error가 남을 수 있어, 이 경로의
  error 폭증까지는 막지 못한다.
- 발생 조건은 FK 위반(팬아웃 중 회원 삭제)이나 DB 장애 같은 드문 경우다.
- id가 앱 재시작·블록 소진마다 최대 500씩 건너뛴다(BIGINT라 문제 없음).

## 9. 다음 단계 (기록만, 이번 범위에서 구현하지 않음)

- **FCM 순차 호출.** DB 구간이 1초대가 되어 종단 시간의 대부분은 FCM 호출일 가능성이 크다.
  `sendEach`/멀티캐스트/병렬화가 후보이지만 실측 없이는 효과를 말할 수 없다 — FCM 지연을 흉내 내는
  별도 측정 설계가 필요하다.
- **이력 저장 분리.** 이력 저장을 별도 트랜잭션(`REQUIRES_NEW`, 배치 단위)으로 분리하면 aborted
  전파와 이력 소실을 근본적으로 막을 수 있다. 설계가 필요한 큰 변경이다.
- `reWriteBatchedInserts` 재측정(체크포인트·autovacuum 같은 변수를 통제한 뒤).
- 10만 건 이상에서 `IN` 일괄 조회 한계 확인.

## 10. `flush/clear` 주기 500의 근거

`FLUSH_INTERVAL = 500`은 100/500/1000 등을 실측 비교해서 고른 값이 아니다 — **최적값을 탐색한
근거는 없다.** 다만 이번 라운드부터는 `hibernate.jdbc.batch_size`, `allocationSize`와 **의도적으로
같은 값**으로 맞췄다(flush가 곧 배치 경계). 이전(IDENTITY)에는 batch_size가 이 경로에서 작동하지
않아 우연히 같은 값이었을 뿐이다.

## 11. 이력서 문장 초안 (2026-10-03 개정)

기준: 세션 누적 수정은 버그 수정이라 제외, N+1은 문제 해결로 쓰되 배수를 앞세우지 않고, 배치
INSERT만 성능 개선으로 쓴다. **DB 구간(FCM 호출 제외), 로컬 측정**이라는 조건을 반드시 함께 적는다.

- **안 A**: 알림 팬아웃에서 회원마다 반복되던 설정·토큰 조회(N+1, 1만 명 기준 2만 회)를 일괄 조회
  2회로 해결하고, 이력 INSERT의 PK 전략을 SEQUENCE로 바꿔 JDBC 배치를 활성화해 회원 1만 명 기준
  DB 구간 소요시간을 21.8초에서 1.05초로 단축(FCM 호출 제외, 로컬 DB 측정).
- **안 B**: 이력 INSERT가 IDENTITY 전략이라 `batch_size=500` 설정이 실제로는 작동하지 않는 것을
  확인하고 SEQUENCE로 전환해 배치 INSERT를 활성화. 회원 1만 명 21.8초 → 1.05초, 5만 명 약 134초 →
  4.6초(DB 구간, FCM 제외).
- **안 C**: 알림 팬아웃의 N+1 조회를 일괄 조회로 해결한 뒤, 남은 병목이던 이력 INSERT를 배치 처리로
  개선해 회원 5만 명 기준 DB 구간을 약 134초에서 4.6초로 단축하고, 이력 저장 실패가 발송을 막지
  않도록 오류 처리를 보강(FCM 호출 제외).

(이전 초안들은 1,073초 기준 누적 결과 또는 N+1의 6.15배를 성과로 썼다 — 위 분류 기준에 맞지 않아
폐기한다.)

## 12. 면접 대비 — 예상 질문

- **"1초면 푸시 1만 건이 1초에 나가나요?"** → 아니다. 측정은 `--fcm.dry-run=true`로 FCM 호출을
  제외한 DB 구간이다. 실제 종단 시간은 회원마다 순차로 붙는 FCM 호출이 지배할 가능성이 크고,
  측정하지 않았다.
- **"N+1은 왜 몇 배라고 안 쓰나요?"** → 쿼리 횟수가 회원 수에 비례해 늘던 구조를 없앤 것이라
  규모에 따라 배수가 달라지는 값이다. 고정 배수는 오해를 낳아서 "2N회 → 2회"로 서술한다. 6.15배는
  1만 명 로컬 조건에서 잰 참고 수치다.
- **"5만 명에서도 같은 배수가 나오나요?"** → 같지 않았다. 1만 명 약 21배, 5만 명 약 29배였다.
  변경 전은 회원당 비용이 올랐고 변경 후는 고정 비용이 분산돼 내려갔다. 변경 전 5만 명은 2회뿐이라
  표본이 작다는 한계가 있다.
- **"flush가 실패하면 어떻게 되나요?"** → 잡아서 error 로그만 남기고 발송은 계속한다. 다만
  트랜잭션이 aborted 되어 이력이 일부 또는 전부 사라질 수 있고, 발송 지속을 우선한 의도적 선택이다.
  근본 해결은 이력 저장을 별도 트랜잭션으로 분리하는 것이다.
- **"`reWriteBatchedInserts`는 왜 안 썼나요?"** → 켰을 때 오히려 느렸지만 옵션 없는 상태에서도
  이상치가 있어 결론을 못 냈다. 이득이 확인되지 않은 옵션은 넣지 않았다.
- **"flush 주기 500과 batch_size 500이 같은데 의도한 건가요?"** → 이번 라운드부터는 의도적이다
  (flush가 배치 경계). 이전에는 IDENTITY라 batch_size가 이 경로에서 작동하지 않아 우연히 같은
  값이었다. 다만 100/500/1000을 비교한 기록은 없어 500이 최적이라는 근거는 없다.
- **"8.1배 전에 N+1도 살아있었던 것 아닌가요?"** → 맞다. 1단계의 before는 세션 누적과 N+1이 둘 다
  포함된 전체 소요시간이라, 8.1배는 세션 관리의 단독 기여가 아니다. 그래서 항상 순차 적용 구조로
  서술하고, 세션 누적 수정 자체는 구현 실수를 고친 선행 버그 수정으로 분류해 성과에서 뺀다.
- **"순서를 바꿨다면 어땠나요?"** → N+1 제거를 먼저 했다면 그쪽이 더 큰 배수를, 세션 관리가 더 작은
  배수를 가졌을 것이다. 역순은 실측하지 않아 추정이며 구체적인 숫자는 없다.
- **"왜 49.8배로 안 쓰나요?"** → 세션 누적 제거와 N+1 제거라는 서로 다른 두 기여를 곱한 값이라,
  하나의 개선이 낸 성과처럼 읽히기 때문이다.
- **"왜 1,073초가 아니라 133초를 기준으로 삼았나요?"** → 1,073초에는 세션 누적이라는 구현 실수가
  섞여 있다. 그 버그를 고친 정상 상태(133초)를 기준점으로 삼아야 이후 개선의 기여만 왜곡 없이
  보여줄 수 있다.

## 재현 방법

```bash
# 0) 인프라 (docs/PERF_STATS_API.md 재현 방법과 동일)
docker compose -f docker-compose.dev.yml up -d postgres redis
docker exec postgres psql -U $POSTGRES_USER -d postgres -c "ALTER SYSTEM SET max_parallel_workers_per_gather = 0;"
docker restart postgres

# 1) 시드 (실행할 때마다 회원 10,000명이 추가되고 트리거용 alert가 1건 만들어진다)
docker exec -i postgres psql -U $POSTGRES_USER -d $POSTGRES_DB < backend/loadtest/seed/seed_notification_data.sql

# 2) fanout-trigger 프로필 + dry-run 기동
cd backend && set -a && source ../.env.dev && set +a && export DB_HOST=localhost
export SPRING_PROFILES_ACTIVE=fanout-trigger
./gradlew bootRun --args='--fcm.dry-run=true'

# 3) 로그에서 확인
#    "회원 팬아웃 완료 - alertId: <alertId>, 대상: 10000명, time=Xms, avg=Yms/명"
```
전체 커맨드는 `backend/loadtest/README.md` 참고.

**재현 시 주의**
- 트리거 도구는 가장 최근 시드 alert를 재사용하므로, **재시드 없이 다시 실행하면 같은 회원 전원에게
  다시 팬아웃**한다. 팬아웃 대상 = 핫 지역에 등록된 회원 전체라서, 시드를 N번 실행하면 대상이
  N × 10,000명이 된다(5만 명 측정 = 시드 5회).
- 변경 전 코드와 비교하려면 별도 worktree에서 같은 DB로 측정한다(`.env`는 gitignore라 복사 필요).
- 앱이 `.env.dev`의 DB를 쓰므로 측정 대상 DB(`POSTGRES_DB`)를 확인할 것. 실행마다
  `user_notification_log`에 대상 인원만큼 행이 쌓인다(로컬 DB 전용).
