# 알림 팬아웃 성능 측정 및 개선

측정일: 2026-09-30. 대상: `AlertNotificationService.triggerNotification()` (회원 알림
발송 구간). 재현 스크립트: `backend/loadtest/`.

## 1. 측정 환경

| 항목 | 값 |
|---|---|
| 회원 규모 | 합성 시드 10,000명 (`backend/loadtest/seed/seed_notification_data.sql`) — 전원 같은 "핫 지역" 관심지역 등록 |
| 트리거 | `fanout-trigger` Spring 프로필 + `NotificationFanoutTriggerTool`(`domain/notification/tool/`) — 시드가 만든 최신 `disaster_alert_id`를 자동으로 찾아 `triggerNotification()` 호출 |
| FCM 처리 | `--fcm.dry-run=true` — 실제 Firebase 호출을 건너뛰고 DB 구간만 격리해서 측정 |
| 반복 횟수 | 각 조건 1회 실측(`/stats` 라운드처럼 3회 반복하지 않음 — 단발 측정이었다는 한계를 그대로 밝힌다) |
| 채택 지표 | 애플리케이션 로그의 "회원 팬아웃 완료 ... time=Xms" 줄 (`@Async`라 HTTP 응답시간으로는 측정 불가) |

## 2. 개선 전 구조와 원인 분리 규명

`triggerNotification()`은 회원 1만 명 순회를 `@Transactional` 메서드 하나로 통째로
감싼다. 회원마다 `sendToMembers()`에서 `NotificationPreference`/`FcmToken`을 개별
조회하는 **N+1 패턴**이 있었고, 이와 별개로 **세션(영속성 컨텍스트) 누적** 문제도
있었다 — 트랜잭션이 끝날 때까지 Hibernate가 관리 엔티티를 계속 쌓아두고, 컨텍스트가
커질수록 매 쿼리 전 더티체킹 비용이 늘어난다.

세션 누적의 근거: `EXPLAIN (ANALYZE, BUFFERS)`로 확인한 DB 쿼리 자체는
0.04~0.05ms인데, 애플리케이션 레벨 소요시간은 루프 진행에 따라 **회원당 31ms →
93ms로 약 3배 증가**했다 — 순수 쿼리 비용이 아니라 세션이 커질수록 앱 레벨에서
따로 비용이 붙는다는 뜻이다.

## 3. 1단계 → 2단계 순차 적용 결과

| 단계 | 조치 | 소요시간 | 이전 단계 대비 |
|---|---|---|---|
| 0 (원본) | 없음 | 1,073,301ms (17분 53초) | — |
| 1단계 | flush/clear 주기 500 적용 (N+1 쿼리는 그대로 유지) | 132,581ms (2분 12.6초) | **약 8.1배** |
| 2단계 | 1단계 + 벌크 조회(JPQL 생성자 프로젝션)로 N+1 제거 | 21,562ms (21.6초) | **추가 약 6.15배** |

**1단계의 8.1배는 세션 누적 제거의 단독 기여가 아니다.** 1단계의 before(1,073,301ms)에는
세션 누적과 N+1 두 원인이 함께 포함되어 있고, N+1이 아직 남아있는 상태에서 세션 문제만
고친 결과가 8.1배다. 각 배수는 항상 "그 단계가 시작된 시점의 소요시간 대비"로 읽어야
한다.

## 4. 왜 "49.8배"를 쓰지 않는가

`1,073,301 / 21,562 ≈ 49.8`은 산술적으로는 맞는 값이다. 하지만 이는 세션 누적 제거와
N+1 제거라는 **서로 다른 두 원인의 기여를 곱한 값**이라, 마치 하나의 개선이 49.8배를
낸 것처럼 읽힌다. 그래서 이 문서에서는 이 값을 단독 수치로 쓰지 않고, 3절의 두 단계
표로만 서술한다.

## 5. 삭제 → 복원 경위 (왜 서술이 두 번 바뀌었는가)

이 수치들의 문서화 이력은 다음과 같이 세 단계를 거쳤다:

1. **PR #261**: 처음 병합 당시 "17분 53초 → 21.6초, 약 49.8배"로 보고.
2. **PR #262**: "49.8배는 두 원인을 뭉뚱그린 수치"라는 지적에 따라, 1단계(8.1배)/2단계(6.15배)로
   분리한 표를 `backend/loadtest/README.md`에 추가.
3. **PR #263**: 그런데 8.1배라는 숫자 자체가 또 "세션 관리만의 성과"처럼 오독될 수 있다는
   지적에, 8.1배 표현까지 문서에서 통째로 제거하고 6.15배(2단계, N+1 제거 기여)만 남김.
4. **이 문서**: 8.1배를 다시 등장시킨다 — 단, 삭제 사유였던 "곱해서 하나의 성과처럼 보이는
   것"의 원인이 8.1배라는 숫자 자체가 아니라 **그 숫자의 프레이밍**(단독 기여처럼 보이게
   쓴 것)에 있었다고 재판단했기 때문이다. "1단계 결과"라고 명시하면 오해가 해소된다는
   것이 이번 판단이며, **수치는 PR #261~263 어디에서도 새로 계산되거나 바뀐 적이 없다** —
   서술 구조(단계 구분)만 추가되었다.

## 6. 적용 순서를 바꿨다면? (정성적 서술만, 실측 없음)

이번 라운드는 세션 관리(flush/clear)를 먼저 적용하고 N+1 제거를 나중에 적용했다. 만약
반대 순서로 적용했다면 — N+1 제거를 먼저, 세션 관리를 나중에 — **N+1 제거 단계가 더
큰 배수를, 세션 관리 단계가 더 작은 배수를 보였을 것**이다. 어느 조치를 먼저 적용하든
그 조치의 before에는 아직 처리되지 않은 나머지 원인의 비용이 섞여 있어서, 순서상
먼저 오는 단계가 항상 더 큰 배수를 갖는 구조이기 때문이다.

**이 역순 시나리오는 실측하지 않았다.** 방향성("더 컸을 것/더 작았을 것")만 서술하며,
구체적인 배수나 소요시간은 지어내지 않는다.

## 7. 최종 결과

**1,073초 → 22초 — 세션 관리(1단계) + N+1 제거(2단계), 두 개선을 순차 적용한 누적
결과.** 단일 개선의 성과로 표기하지 않는다.

## 8. 다음 단계 (기록만, 이번 범위에서 구현하지 않음)

`UserNotificationLog`는 현재 `GenerationType.IDENTITY`를 쓴다. `SEQUENCE` +
`allocationSize`로 전환하면 `application.yml`의 `hibernate.jdbc.batch_size: 500`
설정이 이 INSERT 경로에서도 실제로 작동해(현재는 IDENTITY라 Hibernate가 이 설정을
무시하고 매 INSERT를 즉시 실행함) 회원 1만 건 INSERT 구간에 추가 개선 여지가 있다.
이번 라운드에서는 구현하지 않고 다음 라운드 후보로만 남긴다.

## 9. `flush/clear` 주기 500의 근거

`FLUSH_INTERVAL = 500`은 100/500/1000 등을 실측 비교해서 고른 값이 아니다.
`AlertNotificationService`의 코드 주석에도 명시했듯 "너무 자주도, 너무 뜸하지도
않은 보수적인 출발점"으로 관례적으로 택했다 — **실측으로 최적값을 탐색한 근거는
없다.** 근거가 없다는 사실 자체를 그대로 기록한다.

## 10. 이력서 문장 초안 (3안)

- **안 A**: 회원 1만 명 대상 알림 발송을 두 단계로 개선 — 세션(영속성 컨텍스트) 누적
  문제를 flush/clear 주기 적용으로 해소해 17분 53초→2분 12.6초(8.1배)로 줄인 뒤,
  이어서 N+1 쿼리를 벌크 조회로 제거해 21.6초(추가 6.15배)까지 단축.
- **안 B**: 회원 1만 명 알림 발송 17분 53초 → 21.6초. 세션 누적을 먼저 해소(8.1배)하고,
  그 위에서 N+1을 배치 쿼리로 제거(추가 6.15배)하는 2단계로 진행.
- **안 C**: 회원 1만 명 알림 발송이 17분 53초 걸리는 원인을 세션 누적과 N+1 두 가지로
  분리 규명 — 순차 적용(세션 관리 8.1배 → N+1 제거 추가 6.15배)으로 21.6초까지 개선.

## 11. 면접 대비 — 예상 질문

- **"8.1배 전에 N+1도 살아있었던 것 아닌가요?"** → 맞다. 1단계의 before는 세션 누적과
  N+1이 둘 다 포함된 전체 소요시간이라, 8.1배는 세션 관리의 단독 기여가 아니라 "N+1이
  남아있는 상태에서 세션 문제만 고친 결과"다. 그래서 항상 순차 적용 구조로 서술한다.
- **"순서를 바꿨다면 어땠나요?"** → N+1 제거를 먼저 했다면 그쪽이 더 큰 배수를, 세션
  관리가 더 작은 배수를 가졌을 것이다. 다만 역순은 실측하지 않아 추정이며, 구체적인
  숫자는 없다.
- **"왜 49.8배로 안 쓰나요?"** → 세션 누적 제거와 N+1 제거라는 서로 다른 두 기여를
  곱한 값이라, 하나의 개선이 낸 성과처럼 읽히는 것을 피하기 위해서다.
- **"flush 주기 500과 batch_size 500이 같은데 의도한 건가요?"** → 우연의 일치다.
  확인해보니 `UserNotificationLog`가 `GenerationType.IDENTITY` 전략이라
  `hibernate.jdbc.batch_size`는 이 INSERT 경로에서 애초에 적용되지 않는다(IDENTITY는
  PK를 즉시 받아야 해서 Hibernate가 JDBC 배치를 비활성화한다). `SEQUENCE` +
  `allocationSize`로 전환하면 이 설정을 실제로 활성화할 수 있다 — "설정이 존재한다"와
  "설정이 작동한다"는 다르다.
- **"flush 주기 500은 어떻게 정했나요?"** → 실측으로 최적값을 탐색하지 않았다.
  코드 주석에 남긴 그대로 "너무 자주도, 너무 뜸하지도 않은" 관례적 출발점으로 택한
  값이고, 100/500/1000 등을 비교한 기록은 없다.

## 재현 방법

```bash
# 0) 인프라 (docs/PERF_BASELINE.md 재현 방법과 동일)
docker compose -f docker-compose.dev.yml up -d postgres redis
docker exec postgres psql -U $POSTGRES_USER -d postgres -c "ALTER SYSTEM SET max_parallel_workers_per_gather = 0;"
docker restart postgres

# 1) 시드
docker exec -i postgres psql -U $POSTGRES_USER -d $POSTGRES_DB < backend/loadtest/seed/seed_notification_data.sql

# 2) fanout-trigger 프로필 + dry-run 기동
cd backend && set -a && source ../.env.dev && set +a && export DB_HOST=localhost
export SPRING_PROFILES_ACTIVE=fanout-trigger
./gradlew bootRun --args='--fcm.dry-run=true'

# 3) 로그에서 확인
#    "회원 팬아웃 완료 - alertId: <alertId>, 대상: 10000명, time=Xms, avg=Yms/명"
```
