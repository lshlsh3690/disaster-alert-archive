# 이벤트 클러스터링 평가 — 데이터 파이프라인 단계별 측정

재난문자가 이벤트로 묶이기까지를 **데이터 적재 → 검색 → 생성(병합 판정) → 엔드투엔드** 네 단계로 나누고, 단계마다 사람이 매긴 정답과 비교해 "N개 중 M개"로 센다. 클러스터링은 RAG가 아니지만, 후보를 찾고(검색) 묶을지 정하는(생성) 구조가 같아서 RAG 평가처럼 단계별로 쪼개면 어디서 틀렸는지 가를 수 있다.

> 마지막 측정: 2026-10-23, 분류(사건/비사건) 적용 후 재클러스터링한 평가 사본, 사건 셋 96쌍 기준.
> 이전 측정(개발용 150쌍, 재현율·정밀도 표기)은 `docs/event-clustering/CLUSTERING_QUALITY_REPORT.md`에 기록돼 있다. 그 셋은 아래 4절의 이유로 삭제했다.

---

## 1. 단계와 재는 것

| 단계 | 하는 일 | 정답 | 재는 것 |
|---|---|---|---|
| 데이터 적재 | 알림 저장, 지역(법정동) 매핑, 임베딩 생성, 사건/비사건 분류(`AlertKindClassifier`) | 사람 분류 라벨 450건 | 임베딩·지역이 빠진 알림 수, 사건을 비사건으로 분류한 수 / 비사건을 사건으로 분류한 수 |
| 검색 | 임베딩 경로에서 같은 시군구·7일 안 이벤트 중 본문이 가까운 후보 3개(사고성 유형은 인접 시군구 후보 추가) | 사건 셋 쌍 라벨 | 같은 사건 쌍 중 먼저 온 알림의 이벤트가 나중 알림의 후보에 들어간 수 |
| 생성 | 후보 거리 ≤ 기준값이면 병합, 애매한 사고성 건은 LLM 폴백 판정, 아니면 신규 | 사건 셋 쌍 라벨 | 후보에 있던 같은 사건 쌍 중 묶은 수(판정 실패), 다른 사건 쌍 중 묶은 수(과병합) |
| 엔드투엔드 | 최종 이벤트 배정 | 사건 셋 쌍 라벨 | 과소병합율, 과병합율, 이벤트 구조(단발·시군구 수·기간) |

- **키 경로**(실종 인물, 태풍, 지역 한정 유형, 에피소드형, 광역)는 후보 검색 없이 "유형+시군구" 같은 키로 바로 묶는다. 이 경로의 쌍은 검색·생성으로 나누지 않고 엔드투엔드로만 센다. 경로 구분은 `docs/event-clustering/CLUSTERING_CRITERIA.md` 참고.
- 쌍마다 **나중에 들어온 알림**의 판정을 본다. 먼저 온 알림의 이벤트가 그 시점 후보에 있었는지, 있었다면 묶었는지다.

### 용어
- **과소병합율** = 놓침 ÷ (맞게 묶음 + 놓침). 같은 사건인데 못 묶은 비율.
- **과병합율** = 잘못 묶음 ÷ (맞게 묶음 + 잘못 묶음). 묶은 것 중 다른 사건인 비율.
- 라벨이 "모르겠음"인 쌍과 두 알림 중 하나라도 이벤트에 없는 쌍(미배정)은 비율에서 빼고 개수만 센다.

## 2. 측정 절차

1. **평가 사본**: 운영 스냅샷(2026-10-10, 알림 62,554건)을 로컬 docker Postgres 에 복사한다. 운영 DB 에서는 측정하지 않는다.
2. **분류 채우기**: 사본에서 `AlertKindBackfillTool`(프로필 `alert-kind-backfill`)로 `alert_kind` 를 채운다. 비용을 줄일 때는 라벨된 알림의 시군구·인접 시군구 앞뒤 7일 안 알림만 분류하고, 나머지는 `INCIDENT` 로 채운다(클러스터링에서 `INCIDENT` 와 `null` 은 같게 처리된다).
3. **재클러스터링**: 이벤트 테이블을 비우고 `EventClusteringBackfillTool --backfill.recluster=true` 로 다시 묶는다. 로그를 파일로 남긴다(검색·생성 단계 측정에 쓴다). LLM 폴백은 켠 상태가 기준이다.
4. **엔드투엔드**: `backend/evaluation/eval.sh <DB> <라벨 CSV>` — `eval_rates.sql` 이 라벨 쌍마다 두 알림의 이벤트 번호를 비교해 개수·두 비율·틀린 쌍 목록을 낸다.
5. **검색·생성**: 재클러스터링 로그에는 알림마다 탄 경로, 후보 이벤트와 거리(`event=… dist=…`), 병합 결과가 찍힌다. 이것이 판정 기록이다(추정·재현이 아니라 실제로 일어난 판정).
   - `python parse_log.py <재클러스터링 로그> trace.json` — 로그를 알림별 기록으로 바꾼다.
   - `stage_pairs.sql` 로 라벨 쌍의 시각·최종 이벤트를 뽑고(`pairs.txt`), `python stages.py trace.json pairs.txt` 로 단계별로 센다.
6. **분류 단계**: 사본의 `alert_kind` 를 사람 분류 라벨과 대조한다(특보·안내는 비사건으로 합쳐 센다). 프롬프트를 고칠 때는 사본 없이 라벨 셋만 직접 호출해 잰다(검증 셋 1회 약 $0.03).

비용: 분류 1건과 LLM 폴백 1회가 각각 약 $0.0003(`gpt-4o-mini`). 2026-10-23 측정은 분류 14,498건(약 $4.3) + 재클러스터링 폴백 1,608회(약 $0.5).

- 처음 측정(2026-10-23, 배포본, 450건 전체): 사람이 사건이라 한 151건 중 21건을 비사건으로, 비사건 286건 중 0건을 사건으로 분류했다. 오류는 전부 사건을 비사건으로 빼는 쪽이었고, 원인은 대부분 모델 실수가 아니라 프롬프트가 "단수 예정·방류 예정·행사 공지·정상화 예정"을 비사건으로 정해 둔 기준이 사람 판단과 달랐던 것이다.
- 2026-10-24 사람이 사건/비사건 경계를 다시 정했다(`CLUSTERING_CRITERIA.md` 2절): 단수·정전·가스 공급 중단의 예정·연장·재개, 방류·방류 예정, 행사 진행·종료·통제, 대피권고, 당부가 붙은 실제 사건은 사건 / 행동요령만 알리는 문자, 입산·입수 통제 예고는 비사건.
- 진행 순서: 개발 셋(150, 기존 예시 18개의 출처)으로 오류 원인을 보고 → 검증 셋(100)으로 고치며 확인 → 테스트+R 셋(200)은 마지막에 한 번만 쟀다. 테스트+R 셋은 바뀐 기준에 해당하는 문구(방류·예정·재개·행사·지진·단수·정전 등)가 든 19건을, 분류기 결과를 보지 않고 골라 새 기준으로 다시 라벨했다.
- 남은 오류(테스트+R): 산불 진화 완료 + 예방 당부, 행사 관련 비행훈련 공지 → 비사건 / 산사태 우려 대피 당부 → 사건.
- 측정은 프롬프트 파일을 그대로 읽어 같은 메시지 구조로 `gpt-4o-mini`(temperature 0)를 라벨 셋에만 호출했다(측정 스크립트는 저장소에 두지 않는다). 표본이 작아(사건 73건) 비율은 대략치로 본다. 라벨러 1명.
- 다시 매긴 라벨 54건(2026-10-23 30건 + 10-24 24건)은 `alert-kind-recheck-labels.json`에 원문·유형·지역과 함께 있고, 원래 라벨 파일보다 우선한다.
- 검색·생성·엔드투엔드(3.2~3.4)는 배포본 분류로 잰 값이다. 사건 셋 96쌍은 분류 적용 전후 결과가 쌍 단위로 같아, 분류기를 바꿔도 이 쌍들의 입력은 달라지지 않는다.

## 4. 평가 데이터

| 셋 | 파일 (`backend/evaluation/datasets/`) | 내용 | 용도 |
|---|---|---|---|
| **사건 셋** | `cluster-eval-2026-10-incident.*` | 96쌍(같음 60 / 다름 30 / 모르겠음 6). 두 알림 모두 사건으로 분류된 쌍만, 시스템 결과와 무관하게 무작위 추출. 기준은 `.rubric.md` | 검색·생성·엔드투엔드의 기준 셋 |
| 최종용 | `cluster-eval-2026-10-test.*` | 100쌍. 비사건 제외 후 80쌍이 미배정으로 빠져 16쌍만 계산된다 | 참고 |
| 분류 라벨 | `alert-kind-labels.json`(개발 150), `-val-`(검증 100), `-test-`(100), `-r-`(100), 재판정 `alert-kind-recheck-labels.json`(54, 원문·유형·지역 포함, 퀴즈 `alert-kind-recheck.quiz.html`·`alert-kind-relabel2.quiz.html`) | 사람이 사건/비사건(처음엔 사건·특보·안내)으로 매긴 알림 | 데이터 적재 단계의 분류 측정 |

- **개발용 150쌍(`cluster-eval-2026-10.*`)은 2026-10-24 삭제했다.** 비사건(특보·안내)을 클러스터링에서 빼기 전에 만든 셋이라 되풀이 안내·특보 쌍이 대부분이었고, 비사건 제외 후 150쌍 중 128쌍이 미배정으로 빠져 신뢰할 만한 수치가 나오지 않는다.
- 정답은 사람이 매긴다. LLM이 정답을 매기는 방식(LLM-as-a-Judge)은 쓰지 않는다.
- **사건 셋의 한계**: 같은 분류기가 사건이라 한 알림으로 만든 셋이라, 분류기가 사건을 비사건으로 잘못 뺀 경우는 이 셋에 나타나지 않는다(그 오류는 3.1에서 따로 잰다). 라벨러 1명, 홍수·산사태 쌍 없음, 산불 다른 사건 쌍 1개.
