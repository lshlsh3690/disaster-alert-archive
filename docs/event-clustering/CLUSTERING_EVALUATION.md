# 이벤트 클러스터링 평가 — 데이터 파이프라인 단계별 측정

재난문자가 이벤트로 묶이기까지를 **데이터 적재 → 검색 → 생성(병합 판정) → 엔드투엔드** 네 단계로 나누고, 단계마다 사람이 매긴 정답과 비교해 "N개 중 M개"로 센다. 클러스터링은 RAG가 아니지만, 후보를 찾고(검색) 묶을지 정하는(생성) 구조가 같아서 RAG 평가처럼 단계별로 쪼개면 어디서 틀렸는지 가를 수 있다.

> 마지막 측정: 2026-10-23, 분류(사건/비사건) 적용 후 재클러스터링한 평가 사본, 사건 셋 96쌍 기준.
>
> **2026-11-09 — 이 문서 3·7·8·10절의 "사건 셋" 수치는 지금은 지운 예전 셋으로 잰 기록이다.** 평가 셋은 2026-11 셋(272쌍) 하나로 바꿨다(4절).
> 이전 측정(개발용 150쌍, 재현율·정밀도 표기)은 `docs/event-clustering/CLUSTERING_QUALITY_REPORT.md`에 기록돼 있다. 그 셋은 아래 4절의 이유로 삭제했다.

## 1. 단계와 재는 것

| 단계 | 하는 일 | 정답 | 재는 것 |
|---|---|---|---|
| 데이터 적재 | 알림 저장, 지역(법정동) 매핑, 임베딩 생성, 사건/비사건 분류(`AlertKindClassifier`) | 사람 분류 라벨 450건 | 임베딩·지역이 빠진 알림 수, 사건을 비사건으로 분류한 수 / 비사건을 사건으로 분류한 수 |
| 검색 | 임베딩 경로에서 같은 시군구·7일 안 이벤트 중 본문이 가까운 후보 3개(사고성 유형은 인접 시군구 후보 추가) | 사건 셋 쌍 라벨 | 같은 사건 쌍 중 먼저 온 알림의 이벤트가 나중 알림의 후보에 들어간 수 |
| 생성 | 후보 거리 ≤ 기준값이면 병합, 애매한 사고성 건은 LLM 폴백 판정, 아니면 신규 | 사건 셋 쌍 라벨 | 후보에 있던 같은 사건 쌍 중 묶은 수(판정 실패), 다른 사건 쌍 중 묶은 수(과병합) |
| 엔드투엔드 | 최종 이벤트 배정 | 사건 셋 쌍 라벨 | 과소병합율, 과병합율, 이벤트 구조(단발·시군구 수·기간) |

- **키 경로**(실종 인물, 태풍, 지역 한정 유형, 에피소드형, 광역)는 후보 검색 없이 "유형+시군구" 같은 키로 바로 묶는다. 이 경로의 쌍은 검색·생성으로 나누지 않고 엔드투엔드로만 센다. 경로 구분은 `docs/event-clustering/CLUSTERING_CRITERIA.md` 참고.
- 쌍마다 **나중에 들어온 알림**의 판정을 본다. 먼저 온 알림의 이벤트가 그 시점 후보에 있었는지, 있었다면 묶었는지다.

### 용어
- **과소병합율** = 놓침 ÷ (맞게 묶음 + 놓침). 같은 사건인데 못 묶은 비율.
- **과병합율** = 잘못 묶음 ÷ (맞게 묶음 + 잘못 묶음). 묶은 것 중 다른 사건인 비율.
- 라벨이 "모르겠음"인 쌍과 두 알림 중 하나라도 이벤트에 없는 쌍(미배정)은 비율에서 빼고 개수만 센다.

## 2. 측정 절차

1. **평가 사본**: 운영 스냅샷(2026-10-10, 알림 62,554건)을 로컬 docker Postgres 에 복사한다. 운영 DB 에서는 측정하지 않는다.
2. **분류 채우기**: 사본에서 `AlertKindBackfillTool`(프로필 `alert-kind-backfill`)로 `alert_kind` 를 채운다. 비용을 줄일 때는 라벨된 알림의 시군구·인접 시군구 앞뒤 7일 안 알림만 분류하고, 나머지는 `INCIDENT` 로 채운다(클러스터링에서 `INCIDENT` 와 `null` 은 같게 처리된다). 도구에는 범위 지정 기능이 없어(`--alert-kind.limit`, `--alert-kind.threads` 뿐), 대상 범위를 고르고 나머지를 `INCIDENT` 로 채우는 일은 도구를 돌리기 전에 SQL 로 직접 한다.
3. **재클러스터링**: 이벤트 테이블을 비우고 `EventClusteringBackfillTool --backfill.recluster=true` 로 다시 묶는다. 이벤트를 참조하는 번역·위험도 표(`disaster_event_translation`, `event_region_impact`, `region_risk_index`)도 함께 TRUNCATE 해야 외래 키에 막히지 않는다(명령은 도구 javadoc). 로그를 파일로 남긴다. LLM 폴백은 켠 상태가 기준이다.
4. **엔드투엔드**: 라벨 쌍마다 두 알림의 이벤트 번호를 비교해 맞게 묶음·놓침·잘못 묶음과 두 비율을 센다. 2026-10-23 수치는 SQL 스크립트로 셌고, 그 스크립트는 2026-10-25 저장소에서 지웠다. 앞으로는 Java 단계별 계산(`ADMIN_EVAL_DASHBOARD_DESIGN.md` ④)이 낸다.
5. **검색·생성**: 재클러스터링 로그에는 알림마다 탄 경로, 후보 이벤트와 거리(`event=… dist=…`), 병합 결과가 찍힌다. 3.2·3.3 의 2026-10-23 수치는 이 로그를 판정 기록 삼아 라벨 쌍과 맞춰 센 것이다(추정·재현이 아니라 실제로 일어난 판정). 그때 쓴 임시 파이썬 스크립트는 2026-10-25 저장소에서 지웠다. 판정 기록 테이블(`clustering_trace`)은 2026-11-08 에 들어냈으므로(아래), **검색·생성 단계를 다시 잴 도구는 현재 없다** — 필요하면 재클러스터링 로그를 쓰거나 후보 검색을 SQL 로 재현해야 한다.
6. **분류 단계**: `AlertKindEvalTool`(프로필 `alert-kind-eval`)이 라벨 셋의 알림을 실제 `AlertKindClassifier` 로 분류해(저장 안 함) 사람 라벨과 대조하고 결과를 로그로 남긴다. 특보·안내는 비사건으로 합쳐 센다. `--alert-kind-eval.labels=<라벨 json>` `--alert-kind-eval.override=alert-kind-recheck-labels.json`. 검증 셋 1회 약 $0.03.

비용: 분류 1건과 LLM 폴백 1회가 각각 약 $0.0003(`gpt-4o-mini`). 2026-10-23 측정은 분류 14,498건(약 $4.3) + 재클러스터링 폴백 1,608회(약 $0.5).

- 처음 측정(2026-10-23, 배포본, 450건 전체): 사람이 사건이라 한 151건 중 21건을 비사건으로, 비사건 286건 중 0건을 사건으로 분류했다. 오류는 전부 사건을 비사건으로 빼는 쪽이었고, 원인은 대부분 모델 실수가 아니라 프롬프트가 "단수 예정·방류 예정·행사 공지·정상화 예정"을 비사건으로 정해 둔 기준이 사람 판단과 달랐던 것이다.
- 2026-10-24 사람이 사건/비사건 경계를 다시 정했다(`CLUSTERING_CRITERIA.md` 2절): 단수·정전·가스 공급 중단의 예정·연장·재개, 방류·방류 예정, 행사 진행·종료·통제, 대피권고, 당부가 붙은 실제 사건은 사건 / 행동요령만 알리는 문자, 입산·입수 통제 예고는 비사건.
- 진행 순서: 개발 셋(150, 기존 예시 18개의 출처)으로 오류 원인을 보고 → 검증 셋(100)으로 고치며 확인 → 테스트+R 셋(200)은 마지막에 한 번만 쟀다. 테스트+R 셋은 바뀐 기준에 해당하는 문구(방류·예정·재개·행사·지진·단수·정전 등)가 든 19건을, 분류기 결과를 보지 않고 골라 새 기준으로 다시 라벨했다.
- 남은 오류(테스트+R): 산불 진화 완료 + 예방 당부, 행사 관련 비행훈련 공지 → 비사건 / 홍수주의보·산사태 경보 발령 + 대피 문구, 산사태 우려 대피 당부 → 사건. 1차 수정(사건 2 / 비사건 1) 뒤 입산·입수 통제 예고(비사건)와 방류 예외(사건) 규칙을 더하며 비사건 → 사건이 1 → 3 이 됐다.
- 최종 수치는 `AlertKindEvalTool` 로 쟀다(`gpt-4o-mini`, temperature 0). 같은 프롬프트로 앞서 쓴 Python 측정과 결과가 같은 것을 확인했다. 표본이 작아(사건 73건) 비율은 대략치로 본다. 라벨러 1명.

## 8. 튜닝 전후 비교 방식 (2026-11-07 결정)

튜닝 전후를 **두 비율의 변화로 판단하지 않는다.** 같은 셋을 반복해 쓰므로 쌍이 짝지어져 있고, 짝지은 비교가 비율 비교보다 훨씬 민감하다. `EvaluationRunTool` 이 이전 리포트와 비교해 **고쳐진 쌍 / 새로 틀린 쌍** 목록을 함께 낸다(2026-11-07 구현, `--eval.baseline=<이전 리포트 경로>`).

근거(2026-11-07 재검토에서 실측):

- 사건 셋은 같은 사건이 60쌍뿐이라 과소병합율의 95% 신뢰구간이 ±12%p 수준이다. 2026-10-19 의 48.3%(36.2~60.7%)와 2026-11-07 의 36.7%(25.6~49.3%)는 **구간이 겹쳐**, 비율만으로는 개선인지 표본 요동인지 가를 수 없다. 과병합율은 더 심하다(2/40 → 1.4~16.5%).
- 그런데 두 리포트의 틀린 쌍 목록을 직접 비교하면 **고쳐진 쌍 9개, 새로 틀린 쌍 2개**(`24650`/`27626` 산불, `47189`/`47479` 화재)다. **퇴행 2건이 비율 변화(48.3% → 36.7%)에 가려져 드러나지 않았다.**

따라서 리포트의 1차 산출물은 이 diff 이고, 두 비율은 그대로 두되 2차로 읽는다. 읽는 법은 `CLUSTERING_EVAL_GUIDE.md`.

같은 재검토에서 확인한 이 평가의 한계(아직 해소하지 않음):

- **표본 추출 틀이 시스템의 후보 검색 조건과 같다.** 사건 셋은 "같은 유형 + 같은·인접 시군구 + 7일 이내"에서 뽑았고 이는 임베딩 경로의 블로킹 조건과 사실상 같다. 그 창 밖의 오류(여러 시군구로 번진 산불, 지역을 옮긴 실종자, 30일 초과 이벤트, 최대 939알림·82시군구 이벤트)는 **구조적으로 이 셋에 나타나지 않는다.** 3.4 의 "엔드투엔드"는 엄밀히는 창 안에서의 엔드투엔드다.

- 홀드아웃 셋은 계산되는 같은 사건이 16쌍이라 **1쌍 = 6.2%p** 다. 수치로 인용하지 않는다.

## 9. 판정 기록(`clustering_trace`) 삭제 — 2026-11-08

2026-10-25 결정으로 만들어(PR #312) 운영 수집·백필 양쪽에서 알림마다 한 줄씩 남기던 판정 기록을 **코드에서 들어냈다.**

**왜 지웠나.** 2026-11-07 에 평가 리포트가 잡아낸 퇴행 2건을 처음으로 이 기록으로 진단해 보려다 두 가지를 확인했다.

1. **정작 필요한 순간에 비어 있었다.** 평가 사본 `rp2` 의 이벤트 배정은 기록 기능이 돌기 전에 만들어진 것이라 `clustering_trace` 가 0행이었다. 평가 도구는 재클러스터링을 하지 않고 DB 배정만 읽으므로, 기록을 쓰려면 매번 재클러스터링을 먼저 해야 한다.
2. **기록이 있어도 원인까지는 알려주지 않는다.** 설계상 "그 순간 무엇을 봤는가"만 남기고 "왜"는 남기지 않는다. 실제 원인(화재에만 걸려 있던 LLM 폴백 72h 가드)은 기록이 아니라 코드를 읽어서 찾았다. 기록이 있었어도 `llm_called=false` 까지만 보이고 그 이유는 보이지 않았을 것이다.

반대편 비용은 계속 들고 있었다 — 운영에서 알림마다 INSERT 1회, 재클러스터링마다 TRUNCATE 목록·외래 키 순서·옛 기록 혼입 주의가 늘어난다. **쓰이지 않은 채 복잡도만 늘리는 계측은 없는 편이 낫다고 판단했다**(사용자 결정, 위험도 점수 삭제와 같은 기준).

**같이 사라진 것**: `ClusteringTrace`·`ClusteringTracePath`·`ClusteringTraceResult`·`ClusteringTraceRepository`, `EventClusteringService` 의 기록 배선(12개 메서드에 넘기던 `trace` 인자), 테스트 2개(`ClusteringTraceRepositoryTest`, `EventClusteringServiceTraceTest`).

**남긴 것**: `clustering_trace` 테이블과 V133 마이그레이션. 위험도 때와 같이 **드롭 마이그레이션은 추가하지 않았다** — 되돌릴 여지를 남기려는 것이고, 런타임 코드는 이 표를 더 이상 읽거나 쓰지 않는다.

**잃은 것**: `ADMIN_EVAL_DASHBOARD_DESIGN.md` 의 검색·생성 단계 측정은 데이터 출처가 없어졌다. 그 설계안은 보류 상태다. 틀린 쌍을 들여다보는 대안은 `CLUSTERING_EVAL_GUIDE.md` "틀린 쌍을 들여다보는 법" 절에 적었다(재클러스터링 로그, 후보 검색 SQL 재현).

- 결과: 알림 **1,133건 · 시군구 52곳 · 56일**짜리 산불 블롭(그 안의 870건, 77%가 "예방·입산·소각·건조·캠페인·당부·금지" 문구). 최대 이벤트가 588건 → 996건으로 커졌다.
- 평가 셋의 산불 쌍들이 서로 다른 블롭으로 갈라져 과소병합이 36.7% → 48.3% 로 보였다. **A-1 과는 무관한 왜곡이었다.**
- 함의: 안내성 분리 경로를 2026-10-17 에 지울 수 있었던 것은 분류가 안내 문자를 걸러 주기 때문이다. `alert_kind` 가 `null` 이면 클러스터링한다는 선택(분류 실패가 사건을 빠뜨리지 않게 하려는 것)의 대가가 산불에서는 이 정도로 크다.
- **평가는 반드시 분류가 채워진 사본에서 돌린다.**
