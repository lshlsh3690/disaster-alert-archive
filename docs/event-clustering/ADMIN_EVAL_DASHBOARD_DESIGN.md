# 관리자 페이지 클러스터링 성능 대시보드 — 설계안

> 상태: 설계안(2026-10-25). 구현 전이다. 단계별 평가 방법과 지금까지의 측정 결과는 `CLUSTERING_EVALUATION.md` 를 본다.

## 1. 목표

관리자 페이지에서 **운영 데이터로** 클러스터링 파이프라인의 단계별 성능을 "N개 중 M개"로 본다.

| 단계 | 보는 것 |
|---|---|
| 데이터 적재 | 알림 저장·임베딩·지역 매핑·사건/비사건 분류가 제대로 됐는가 |
| 검색 | 같은 사건 쌍에서 먼저 온 알림의 이벤트가 나중 알림의 후보에 들어갔는가 |
| 생성 | 후보에 든 쌍을 맞게 묶거나 나눴는가 |
| 엔드투엔드 | 최종 이벤트 배정의 과소병합율·과병합율, 이벤트 구조 |

지금은 평가 사본에서 재클러스터링하고 사람이 매긴 표본(사건 셋 96쌍, 분류 라벨 450건)으로만 잴 수 있다. 운영에서 계속 보려면 **정답**과 **판정 기록**이 운영에도 있어야 한다.

## 2. 결정 사항 (2026-10-25)

- **판정 기록을 운영 수집 경로에서도 남긴다.** 이전에는 평가 사본 재클러스터링(백필) 때만 남기기로 했으나, 검색·생성 단계를 운영 데이터로 보려면 쌍마다 "후보에 있었는가, 몇 거리였는가, 어떻게 판정됐는가"가 필요하다.
- **LLM 판사(LLM-as-a-Judge)를 도입한다.** 운영 표본의 정답을 사람 대신 판사가 매긴다. 판사 답은 사람 정답이 아니므로, 판사가 사람 라벨과 얼마나 일치하는지를 화면에 함께 보인다.
- **계산은 "N개 중 M개" 세기만 한다.** 비율 외의 지표(가중치, 일치도 계수 등)는 넣지 않는다.

## 3. 전체 흐름

```
[운영 수집] 알림 → 사건/비사건 분류 → 클러스터링 ──→ ① 판정 기록 저장 (알림마다 1줄)

[관리자 버튼 또는 주기 실행]
  ② 최근 N일에서 표본 뽑기 (알림 쌍, 알림 1건)
  ③ 판사가 정답 매김 ("같은 사건?", "사건/비사건?")
  ④ 판정 기록 × 판사 정답 → 단계별 N개 중 M개 → 결과 테이블 저장

[관리자 페이지] ⑤ 회차별 결과 표 + 추이
```

## 4. 구성 요소

### ① 판정 기록 `clustering_trace` (알림 1건당 1줄)

| 컬럼 | 내용 |
|---|---|
| `alert_id` | 알림 id (PK) |
| `path` | `EMBEDDING`, `REGIONAL`(지역 한정), `EPISODIC`, `PERSON`(신원 키), `GLOBAL_TYPE`(태풍), `BROADCAST`, `NO_REGION`, `SKIPPED`(비사건 제외) |
| `candidates` | 같은 시군구 후보 이벤트와 거리 JSON `[{"event":15918,"dist":0.387}]` |
| `adjacent_candidates` | 인접 시군구 후보(사고성 유형만) JSON, 없으면 null |
| `threshold` | 적용된 병합 기준 거리 |
| `llm_called` / `llm_result` | LLM 폴백 호출 여부, 고른 이벤트 id(없으면 null) |
| `result` | `MERGED` / `NEW` / `SKIPPED` |
| `event_id` | 최종 배정 이벤트 |
| `created_at` | 기록 시각 |

`path` 와 `EventClusteringService` 의 대응(`CLUSTERING_CRITERIA.md` 3절 순서):

| `path` | 어디서 끝나는가 | `candidates` / `threshold` |
|---|---|---|
| `SKIPPED` | `clusterNewAlert` 앞단 — 비사건(`ADVISORY`) 또는 본문이 빈 알림. `result=SKIPPED`, `event_id` null | null / null |
| `PERSON` | `clusterPerson` | null / null |
| `GLOBAL_TYPE` | `clusterGlobalType` — 유형이 태풍이면 발송 시군구 수와 무관하게 여기로 온다. 키는 유형만 | null / null |
| `REGIONAL` | `clusterRegionalType`(인접 시군구 산불 병합 `mergeIntoAdjacentRegionalEvent` 포함) | null / null |
| `EPISODIC` | `clusterEpisodicType`, 시군구 1개 | null / null |
| `BROADCAST` | `clusterBroadcast` — 발송 시군구 수가 기준: 10개 초과, 또는 에피소드형 유형이 2개 이상. 키는 시도+유형(시도 8개 이상이면 전국+유형) | null / null |
| `NO_REGION` | 임베딩 경로에 왔는데 지역 코드가 없음(항상 신규) | null / null |
| `EMBEDDING` | 임베딩 경로 후보 검색·임계값·인접·LLM 폴백 | 후보 목록(0건이면 `[]`) / 적용한 병합 거리 상한 |

- `candidates` 는 `[]`(검색했는데 0건)와 null(검색하지 않는 경로)을 구분한다. `adjacent_candidates` 는 인접 후보를 실제로 조회했을 때만 채운다(사고성 유형이고 같은 시군구 병합에 실패한 경우). 같은 시군구에서 병합되면 null 이다.
- `llm_called` 는 LLM 폴백(`pickSameGeneralIncident`)을 실제로 호출했을 때만 true 다. 게이트(유형·borderline 후보·후보 이벤트 가드)에서 걸러져 호출하지 않았으면 false.
- `clusterNewAlert` 안에서 예외가 나 이벤트 배정이 끝나지 않은 알림은 **기록하지 않는다**(결과를 모르므로). 이 경우는 이미 `log.error` 로 남고, ④의 "판정 기록 없음"에 저장 실패와 함께 잡힌다.
- 새 Flyway 마이그레이션으로 테이블을 만든다. 이미 적용된 마이그레이션은 건드리지 않는다. 외래 키는 두지 않는다 — `event_id` 가 가리키는 이벤트는 재클러스터링·cross-region 병합 때 지워지고, 이 표는 판정 순간의 기록이라 지워진 이벤트 id 도 그대로 남아야 한다.
- `EventClusteringService` 가 판정 중에 이미 아는 값을 모아 `clusterNewAlert` 끝에서 한 번 저장한다. 판정 로직은 바꾸지 않는다.
- **저장 실패는 수집을 막지 않는다.** 예외를 삼키고 `warn` 로그만 남긴다(분류 저장 LazyInitializationException 사고 참고). JPA 엔티티 merge 가 아니라 `JdbcTemplate` 단일 UPSERT 로 쓰고, 클러스터링 트랜잭션과 분리된 별도 트랜잭션(`REQUIRES_NEW`)에서 실행한다 — 같은 트랜잭션에서 SQL 이 실패하면 Postgres 가 트랜잭션 전체를 중단 상태로 만들어 클러스터링 결과(매핑·이벤트)까지 커밋되지 않기 때문이다(`DeadTokenCleanupService` 와 같은 이유).
- 같은 알림을 다시 클러스터링하면(백필) 기존 줄을 덮어써 알림당 1줄을 유지한다.
- 원문·임베딩은 넣지 않는다(`disaster_alert` 에 있음). cross-region 패스(동물 탈출)는 범위 밖.
- 하루 수백 줄 수준이다.

### ② 표본 뽑기

- **쌍 표본**: 최근 N일 알림 중 같은 유형, 같은·인접 시군구, 발송 간격 7일 이내인 쌍을 시스템 결과와 무관하게 무작위로 뽑는다(사건 셋을 만든 방식과 같음). 판정 기록이 있는 알림만 대상으로 한다. 판정 기록이 없는 알림 수는 회차마다 데이터 적재 단계에 함께 표시해, 저장 실패로 표본에서 조용히 빠진 알림이 보이게 한다(수집을 막지 않는 원칙은 유지).
- **알림 표본**: 분류 단계용으로 최근 N일 알림을 무작위로 뽑는다(사건·비사건 모두).
- 기본값 예: 쌍 300개, 알림 100건. 실행 시 바꿀 수 있게 한다.
- **실종자(`PERSON`)·태풍(`GLOBAL_TYPE`) 경로는 이번 표본 대상에서 뺀다.** 실종자는 지역 무관·14일, 태풍은 전국이 같은 사건 범위라 위 조건(같은·인접 시군구, 7일)으로는 거의 뽑히지 않는다. 두 경로를 대표하는 표본 조건은 나중에 따로 정한다(6절).

### ③ 판사

- 모델: `gpt-4o`. 클러스터링 LLM 폴백(`gpt-4o-mini`)과 같은 모델을 쓰면 같은 실수를 같이 하므로 다른, 더 강한 모델을 쓴다.
- 쌍 판정: 두 알림 원문·유형·지역·시각 + `CLUSTERING_CRITERIA.md` 1절 "같은 사건의 정의"를 주고 `SAME` / `DIFF` 한 단어로 답하게 한다.
- 분류 판정: 알림 원문 + `CLUSTERING_CRITERIA.md` 2절 사건/비사건 경계를 주고 `INCIDENT` / `ADVISORY` 로 답하게 한다.
- 정확히 읽히지 않는 답은 "판사 판정 불가"로 따로 센다(추측하지 않음). 답은 정해진 한 단어와 정확히 같을 때만 받는다(앞뒤 공백·대소문자 무시). 부정문·여러 단어·두 답이 섞인 답은 판정 불가다.
- 온도는 0. 모델은 공유 `ChatModel` 설정(`gpt-4o-mini`)이 아니라 호출마다 `gpt-4o` 로 지정한다(`OpenAiTranslationClient` 와 같은 방식).
- **프롬프트**: `backend/src/main/resources/judge/` 의 시스템 프롬프트 두 개(쌍·분류). 판정 기준 부분은 `CLUSTERING_CRITERIA.md` 1절·2절을 그대로 옮긴 것이고, 기준 문서를 고치면 이 파일도 같이 고친다(회차에 파일 해시를 남기는 것은 ⑤ `evaluation_run`). 예시(few-shot)는 넣지 않는다 — 사람 라벨에서 예시를 뽑으면 그 라벨로 재는 신뢰도가 부풀기 때문이다. 분류기(`alert-kind/`) 프롬프트도 재사용하지 않는다(같은 프롬프트면 같은 실수를 같이 한다). 기준 문서에서 옮기지 않거나 더한 문장이 있다: 분류 프롬프트에는 2절의 "애매하면 비사건으로 답하게 한다"를 **넣지 않는다**(분류기의 답 규칙이고, 판사는 사람 라벨을 흉내 내야 한다). 대신 2절의 "실종 수배는 사건" 한 줄과 사건/비사건 ↔ `INCIDENT`/`ADVISORY` 대응 줄을 둔다. 쌍 프롬프트에는 "두 문자는 발송 시각 순서(알림 1이 먼저)로 주어진다"를 더한다(1번 "후속 문자" 판단에 순서가 필요하다).
- **입력**: 쌍은 두 알림 각각 `[유형] [수신 지역(original_region)] [발송 시각]` + 원문. 분류는 `[유형]` + 원문. 원문 공백은 하나로 줄인다.
- **판사 신뢰도**: 사람 라벨이 있는 표본에 판사를 돌려 아래를 센다. 판사 프롬프트나 모델을 바꿀 때마다 다시 잰다.
  - 쌍(사건 셋 90쌍, 모르겠음 6쌍 제외): 사람이 같다고 한 N쌍 중 판사도 같다 M쌍, 사람이 다르다고 한 N쌍 중 판사도 다르다 M쌍
  - 분류(테스트+R 셋 200건, 재판정 라벨 `alert-kind-recheck-labels.json` 우선, 모르겠음 제외, 특보·안내는 비사건으로 합침): 사람이 사건이라 한 N건 중 판사도 사건 M건, 사람이 비사건이라 한 N건 중 판사도 비사건 M건. 한계: 이 셋은 분류기 프롬프트를 고친 뒤 마지막에 한 번 재는 셋이었지만, 그 결과를 본 뒤 입산·입수 통제 예고(비사건)와 방류 예외(사건) 규칙을 더하고 일부 라벨을 새 기준으로 다시 매겼다(`CLUSTERING_EVALUATION.md` 3.1). 판사 프롬프트는 이 기준을 옮긴 것이라, 이 셋은 기준 정제에 쓰이지 않은 셋이 아니며 여기서 나온 일치도는 낙관적일 수 있다. 운영 표본의 정답을 판사에게 맡기는 근거로 쓸 때는 이 점을 감안하고, 기준 정제에 쓰이지 않은 별도 셋이 생기면 다시 잰다.
  - 판정 불가는 분모에서 빼고 개수만 따로 센다.
  - 측정은 `JudgeReliabilityTool`(프로필 `judge-reliability`)이 로컬 평가 사본에서 하고 결과를 로그로 남긴다. 결과를 테이블에 저장하는 것은 ⑤ 단계다.

### ④ 단계별 계산 (판사 답을 정답으로)

쌍마다 나중에 들어온 알림의 판정 기록을 본다.

| 단계 | 대상 (분모) | 오류 (M) |
|---|---|---|
| 데이터 적재 — 누락 | 기간 내 전체 알림 | 임베딩 없음, 지역 매핑 없음, 분류 실패(`alert_kind` null), **판정 기록 없음**(저장 실패 또는 클러스터링 중 오류. 이 알림은 검색·생성·엔드투엔드 표본에서 빠진다. 판정 기록 배포 시점을 저장해 두고 **그 이후 알림만** 센다 — 배포 전 알림은 기록이 없는 게 정상이다) |
| 데이터 적재 — 분류 | 판사가 사건이라 한 알림 / 비사건이라 한 알림 | 분류기가 비사건으로 분류 / 사건으로 분류 |
| 검색 | 판사 `SAME` 이고 나중 알림이 `EMBEDDING` 경로인 쌍 | 먼저 알림의 이벤트가 `candidates`·`adjacent_candidates` 에 없음 |
| 생성 | 위에서 후보에 든 쌍 / 판사 `DIFF` 인데 후보에 든 쌍 | 안 묶음 / 묶음 |
| 키 경로 | 판사 `SAME`·`DIFF` 이고 나중 알림이 키 경로인 쌍 | 같은데 안 묶음 / 다른데 묶음 |
| 엔드투엔드 | 판사 `SAME` 쌍 / 시스템이 묶은 쌍 | 놓침(과소병합) / 판사 `DIFF`(과병합) |
| 엔드투엔드 — 구조 | 기간 내 이벤트 | 단발 이벤트, 시군구 10개 이상, 기간 30일 초과 (판사 불필요) |

- 모르겠음·판정 불가·미배정 쌍은 분모에서 빼고 개수만 따로 센다.
- 계산은 `AlertKindScore` 처럼 순수 로직 클래스로 두고 단위 테스트로 지킨다.

### ⑤ 결과 저장과 관리자 페이지

#### 오류는 두 종류로 나뉜다

| 종류 | 무엇 | 어떻게 아는가 | 범위 |
|---|---|---|---|
| **전수 오류** | 임베딩 누락, 지역 매핑 누락, 분류 실패(`alert_kind` null), 판정 기록 저장 실패 | 정답 없이 DB·로그로 바로 앎 | 기간 내 **모든 알림**을 날짜별로 센다 |
| **표본 오류** | 분류 오판, 검색 실패, 판정 실패, 과병합, 키 경로 오류, 과소병합 | 판사 정답과 비교해야 앎 | 평가 회차에서 뽑은 **표본 안에서만** 나온다 |

표본 오류의 날짜별 건수는 "그날 들어온 알림 중 표본에 뽑힌 것" 기준이라, 그날 전체 오류 수가 아니라는 점을 화면에 밝힌다.

#### 저장

- `evaluation_run` — 회차: 실행 시각, 대상 기간, 표본 크기, 판사 모델, 분류 프롬프트 버전, **판사 프롬프트 버전·판정 기준(`CLUSTERING_CRITERIA.md`) 버전**(파일 해시), 판사 신뢰도 두 숫자, 비용 추정. 기준이나 프롬프트가 바뀐 회차끼리는 추이 화면에서 구분해 보여 준다.
- `evaluation_stage_result` — 회차 × 단계: 분모, 오류 수.
- `evaluation_error` — **오류 1건당 1줄.** 대시보드에서 "언제, 어떤 문자에서" 났는지 보기 위한 테이블.

| 컬럼 | 내용 |
|---|---|
| `id`, `run_id` | 오류 id, 회차(전수 오류는 null) |
| `stage` | `LOAD`(데이터 적재), `RETRIEVAL`(검색), `DECISION`(생성), `KEY_PATH`, `END_TO_END` |
| `error_type` | `EMBEDDING_MISSING`, `REGION_MISSING`, `KIND_UNCLASSIFIED`, `INCIDENT_AS_ADVISORY`, `ADVISORY_AS_INCIDENT`, `NOT_IN_CANDIDATES`, `NOT_MERGED`, `WRONG_MERGE` 등 |
| `occurred_at` | 오류가 난 시점 = **문제가 된 알림(쌍이면 나중 알림)의 수신 시각**. 날짜별 집계 기준 |
| `alert_id`, `pair_alert_id` | 문제 알림, 쌍의 상대 알림(먼저 온 알림, 쌍 오류만) |
| `disaster_type`, `sigungu` | 필터용 유형·시군구 |
| `path`, `distance`, `threshold`, `llm_called`, `llm_result` | 그 순간의 판정 기록 요약(판정 기록에서 복사) |
| `judge_answer`, `system_result` | 판사 답과 시스템 결과(표본 오류만) |

원문은 복사하지 않고 `alert_id` 로 `disaster_alert` 에서 읽는다.

#### 백엔드 API (관리자 권한 `@PreAuthorize("hasRole('ADMIN')")`, 응답은 `ApiResponse`)

- `GET /api/v1/admin/evaluation/runs` — 회차 목록과 단계별 "N개 중 M개"
- `GET /api/v1/admin/evaluation/errors/daily?from=&to=&stage=` — 날짜 × 단계별 오류 건수(전수·표본 구분)
- `GET /api/v1/admin/evaluation/errors?date=&stage=&type=&disasterType=&page=` — 오류 목록. 행마다 원문(쌍이면 두 개), 유형, 지역, 시각, 경로, 거리, 기준값, LLM 결과, 판사 답
- `POST /api/v1/admin/evaluation/runs` — 평가 실행(판사 호출 비용이 들므로 관리자만, 동시 실행 1개)

#### 화면 (관리자 페이지)

1. **요약**: 최근 회차의 단계별 "N개 중 M개" 표와 판사 신뢰도.
2. **날짜별 오류**: 날짜 × 단계 막대 그래프. 전수 오류와 표본 오류를 구분해 표시. 막대를 누르면 그날 오류 목록으로 이동.
3. **오류 목록**: 날짜·단계·오류 종류·재난 유형으로 거른다. 행을 펼치면 원문, 그 순간의 판정 기록(경로, 후보 이벤트와 거리, 기준값, LLM 결과), 판사 답을 보여 주고, 해당 이벤트 상세로 갈 수 있다.
4. **회차별 추이**: 단계별 오류 비율의 회차별 변화(튜닝 전후 비교).

검색·생성 수치와 오류에는 "판정 기록 배포 이후 알림만"이라고 적는다.

## 5. 비용

| 항목 | 예상 |
|---|---|
| 판정 기록 | LLM 호출 없음. 알림 1건당 INSERT 1번 |
| 평가 1회 (쌍 300 + 알림 100, `gpt-4o`) | 약 $0.5~1 |
| 판사 신뢰도 측정 (사람 라벨 약 200건) | 약 $0.3~0.5, 판사를 바꿀 때만 |

처음에는 관리자 버튼으로만 실행한다. 주기 자동 실행은 비용이 계속 나가므로 나중에 정한다.

## 6. 제약과 한계

- 검색·생성 수치는 ① 배포 이후 클러스터링된 알림만 나온다. 과거 알림에는 판정 기록이 없다.
- 판사 정답은 사람 정답이 아니다. 판사 신뢰도가 낮으면(예: 사람과 어긋나는 쌍이 많으면) 그 회차 수치를 믿지 않는다.
- 표본이 수백 쌍이라 비율은 대략치다.
- 실종자·태풍 경로는 표본에서 빠지므로, 그 경로의 오류(예: 지역을 옮긴 같은 실종자가 다른 이벤트로 갈라짐)는 대시보드 수치에 나타나지 않는다. 두 경로는 전체 알림에서 비중이 작아 이번 범위에서 미룬다.
- **판정 기록이 클러스터링보다 먼저 커밋된다.** 기록은 `REQUIRES_NEW` 로 `clusterNewAlert` 끝에서 즉시 커밋되고, 클러스터링 트랜잭션은 그 뒤에 커밋된다. 그 커밋이 실패하면(커밋 순간의 연결 장애 등) 이벤트·매핑은 롤백되고 기록만 남아, 존재하지 않는 `event_id` 를 가리키는 `NEW`/`MERGED` 행이 생긴다. 드물고 같은 알림을 다시 클러스터링하면 덮어써지므로 받아들인다(2026-10-25). 계산에서 `event_id` 로 이벤트를 조인할 때 이벤트가 없는 기록은 따로 세어 드러낸다. 같은 트랜잭션의 savepoint(`NESTED`)로 바꾸면 없앨 수 있다.
- **LLM 호출 실패와 "같은 사건 없음"이 구분되지 않는다.** `EventLLMDecisionService.callAndParse` 가 호출 예외·응답 파싱 실패를 삼키고 null 을 돌려줘, 기록에는 둘 다 `llm_called=true`, `llm_result=null` 로 남는다. OpenAI 장애 시간대의 폴백 실패가 "LLM 이 없음으로 판정"으로 집계되므로, ④ 생성 단계 계산을 만들 때 이 구분을 다시 정한다.

## 7. 구현 순서

| 순서 | 작업 | 이유 |
|---|---|---|
| 1 | ① 판정 기록 (운영 기록) | 배포한 날부터 데이터가 쌓이므로 가장 먼저 |
| 2 | ③ 판사 + 판사 신뢰도 측정 | 판사를 믿을 수 있는지부터 확인 |
| 3 | ② 표본 뽑기 + ④ 단계별 계산 + 결과·오류 테이블(`evaluation_run`, `evaluation_stage_result`, `evaluation_error`) | 판정 기록이 며칠 쌓인 뒤 |
| 4 | ⑤ 관리자 API·화면 (요약 → 날짜별 오류 → 오류 목록 → 회차별 추이) | 결과가 저장되기 시작한 뒤 |

전수 오류(임베딩·지역 누락, 분류 실패)는 판사 없이 DB 만 세면 되므로, 3 이전에도 날짜별 화면을 먼저 만들 수 있다.

각 단계는 백엔드 TDD(`tdd-developer` RED → 사용자 확인 → GREEN → `code-reviewer`)로 진행하고, 배포 전 평가 사본에서 먼저 동작을 확인한다.
