# 클러스터링 평가 읽는 법

이벤트 클러스터링이 잘 묶었는지를 사람이 라벨한 알림 쌍으로 재는 도구의 설명서다. 계산은 일부러 단순하게 두었다.

## 하는 일 한 줄
사람이 라벨한 **알림 쌍**마다 "두 알림이 **같은 이벤트**에 들어 있는가"만 본다.

## 쌍 하나가 어떻게 세어지나
| 사람의 라벨 | 시스템 | 세는 이름 |
|---|---|---|
| 같은 사건 | 같은 이벤트 | **맞게 묶음** |
| 같은 사건 | 다른 이벤트 | **놓침** |
| 다른 사건 | 같은 이벤트 | **잘못 묶음** |
| 다른 사건 | 다른 이벤트 | 세지 않는다 |

## 점수 하나와 그 재료 둘
위의 세 개수(맞게 묶음·놓침·잘못 묶음)에서 **계산만** 한다. 새로 재는 값은 없다. 셋 다 **높을수록 좋다**.

- **맞게 묶은 비율** = 맞게 묶음 ÷ (맞게 묶음 + 잘못 묶음). 시스템이 묶은 쌍 중 사람도 같은 사건이라 한 비율. 잘못 묶을수록 내려간다. (= 100 − 과병합율)
- **빠짐없이 묶은 비율** = 맞게 묶음 ÷ (맞게 묶음 + 놓침). 사람이 같은 사건이라 한 쌍 중 시스템이 묶은 비율. 놓칠수록 내려간다. (= 100 − 과소병합율)
- **점수** = 맞게 묶은 비율과 빠짐없이 묶은 비율의 **조화평균** = 2 × 맞게 묶음 ÷ (2 × 맞게 묶음 + 놓침 + 잘못 묶음). 반올림된 두 비율을 다시 조합하지 않고 개수로 바로 계산한다.

**그냥 평균이 아니라 조화평균인 이유** — 둘 중 낮은 쪽으로 끌려 내려가서, 한쪽만 좋은 결과를 제대로 낮게 매긴다.

| 클러스터링 | 맞게 묶은 비율 | 빠짐없이 묶은 비율 | 그냥 평균 | 점수(조화평균) |
|---|---|---|---|---|
| 2026-11-11 develop, 2026-11 셋(사본 `disaster_alert_eval_v5`, 문맥 재확인 라벨) | 89.5% | 70.3% | 79.9 | **78.8** |
| 모든 알림을 이벤트 하나로 묶음 | 5% | 100% | 52.5 | **9.5** |
| 모든 알림을 따로 둠 | (묶은 쌍 없음) | 0% | — | **0** |

예전 리포트의 **과소병합율·과병합율**(낮을수록 좋음)은 빠짐없이 묶은 비율·맞게 묶은 비율을 뒤집은 값이라, 리포트에서 괄호 안에 함께 적는다.

> 2026-10-19 에 지표를 두 비율로 줄였던 이유는 "혼자 읽고 판단할 수 있어야 한다"였다. 2026-11-09 에 품질을 점수 하나로 매기기 위해 점수를 더했고, 같은 이유로 영어 용어(precision/recall/F1) 대신 쉬운 말을 쓴다 — 처음엔 순도·완성도라 불렀다가 뜻이 헷갈려 같은 날 **맞게 묶은 비율·빠짐없이 묶은 비율**로 바꿨다(계산은 그대로). 지표를 이 셋 밖으로 더 늘리지 않는다.

### 예시 (쌍 6개)
| 쌍 | 사람 | 시스템 | 세는 이름 |
|---|---|---|---|
| 1 | 같은 사건 | 같은 이벤트 | 맞게 묶음 |
| 2 | 같은 사건 | 같은 이벤트 | 맞게 묶음 |
| 3 | 같은 사건 | 다른 이벤트 | 놓침 |
| 4 | 같은 사건 | 다른 이벤트 | 놓침 |
| 5 | 다른 사건 | 같은 이벤트 | 잘못 묶음 |
| 6 | 다른 사건 | 다른 이벤트 | (세지 않음) |

- 맞게 묶은 비율 = 2 ÷ (2 + 1) = 66.7%. 묶은 3쌍 중 2쌍이 맞았다. (과병합율 33.3%)
- 빠짐없이 묶은 비율 = 2 ÷ (2 + 2) = 50.0%. 같은 사건 4쌍 중 2쌍을 묶었다. (과소병합율 50.0%)
- 점수 = 2 × 2 ÷ (4 + 2 + 1) = 57.1점.

## 평가에서 빠지는 쌍
- **모르겠음**: 라벨이 "모르겠음"인 쌍.
- **이벤트 미배정**: 두 알림 중 하나라도 이벤트에 들어 있지 않은 쌍(비사건으로 분류되어 클러스터링에서 빠졌거나 처리되지 않은 알림). 정답을 가릴 수 없어서 빼고 건수만 센다.
- 두 건수는 리포트에 따로 적힌다. 둘 다 해당하면 모르겠음으로 센다.
- **알림 단위 점수(B-cubed)는 다르다.** `--eval.bcubed` 로 내는 점수에서 미배정 알림은 빼지 않고 혼자인 이벤트로 계산한다. 시스템이 못 묶은 알림을 빼면 못 묶을수록 점수가 오르기 때문이다. 모르겠음(분류 불가)만 뺀다.

## 리포트
```
## 요약
- 점수 76.5점 — 맞게 묶은 비율과 빠짐없이 묶은 비율의 조화평균
- 맞게 묶은 비율 92.9% — 묶은 42쌍 중 39쌍 맞음, 3쌍 잘못 묶음 (과병합율 7.1%)
- 빠짐없이 묶은 비율 65.0% — 같은 사건 60쌍 중 39쌍 묶음, 21쌍 놓침 (과소병합율 35.0%)
- 제외: 모르겠음 6쌍, 이벤트 미배정 0쌍
## 놓친 쌍 / 잘못 묶은 쌍
| alertA | alertB | 유형 | 같은 시군구 | 간격(시간) | 본문 거리 | 종류 |
```
(위 숫자는 설명용 예시다.) 놓친 쌍과 잘못 묶은 쌍에는 **이유를 계산하지 않고 사실만** 적는다.
- 유형: 두 알림의 재난 유형(다르면 "A/B").
- 같은 시군구: 두 알림이 시군구(법정동 코드 앞 5자리)를 하나라도 공유하면 "예".
- 간격(시간): 두 알림 발송 시각의 차.
- 본문 거리: 두 알림 본문 임베딩의 코사인 거리(작을수록 비슷, 병합 기준은 0.15 이하). 임베딩이 없으면 "-".
- 종류: `놓침`(같은 사건인데 안 묶음) 또는 `잘못 묶음`(다른 사건인데 묶음). 2026-11-07 에 추가한 칸이라 그 전 리포트에는 없다.

## 튜닝 전후 비교
**점수나 비율의 변화로 개선 여부를 판단하지 않는다.** 같은 셋을 반복해 쓰므로 쌍 단위로 비교하는 편이 훨씬 민감하다(근거: `CLUSTERING_EVALUATION.md` 8절).

두 리포트를 비교하면 된다: `git diff --no-index <이전 리포트>.md <새 리포트>.md`. 틀린 쌍 표는 라벨 파일 순서로 나오므로, `-` 줄은 이번에 사라진 쌍, `+` 줄은 새로 틀린 쌍이다. 점수 줄도 같이 보인다.

도구 안의 이전 리포트 비교(--eval.baseline, 2026-11-10 삭제)는 리포트에 절 하나를 붙이는 데 비해 코드가 많아 없앴다. 평가에서 빠진 쌍도 표에서 사라지므로, 요약의 "제외" 줄이 이전과 같은지 먼저 확인한다.

## 틀린 쌍을 들여다보는 법
리포트의 틀린 쌍은 사실만 적혀 있고 **왜 그렇게 됐는지는 적히지 않는다.** 원인은 사람이 따로 찾는다.

판정 순간을 기록하던 `clustering_trace` 테이블은 **2026-11-08 에 들어냈다**(경위는 `CLUSTERING_EVALUATION.md` 9절). 그래서 지금 쓸 수 있는 수단은 둘뿐이다.

1. **재클러스터링 로그** — 알림마다 탄 경로와 병합 결과가 찍힌다. 후보 이벤트와 거리(`event=… dist=…`)는 **임베딩 경로(일반 후보 검색)에서만** 찍힌다. 동물 경로(`clusterAnimal`)는 후보 수와 선택된 이벤트만 남기고 후보 목록·거리는 남기지 않으므로 로그를 보존해도 동물 후보는 확인할 수 없다. 재클러스터링할 때 로그를 파일로 남겨 두면 그 실행에 한해 판정을 되짚을 수 있다.
2. **후보 검색을 SQL 로 재현** — 나중에 들어온 알림 기준으로 "같은 시군구 + 후보 윈도우(168h) 안 이벤트"를 거리순으로 다시 뽑아 본다. `findTopCandidates` 처럼 윈도우는 **이벤트의 마지막 알림 시각**(판정 시점 이전)으로 검사하고 broadcast 이벤트는 뺀다. 그래도 그 순간 실제로 본 후보가 아니라 **지금 이벤트 배정으로 다시 계산한 값**이라는 한계가 있다.

```sql
-- 먼저 들어온 알림이 속한 정답 이벤트
SELECT event_id FROM disaster_alert WHERE disaster_alert_id = <먼저 알림 id>;

-- 나중 알림 기준으로 같은 시군구·168h 안 후보를 거리순으로 재현
WITH t AS (SELECT embedding, created_at FROM disaster_alert WHERE disaster_alert_id = <나중 알림 id>),
     s AS (SELECT DISTINCT left(legal_district_code,5) c FROM disaster_alert_region WHERE disaster_alert_id = <나중 알림 id>)
SELECT a.event_id, round(min(a.embedding <=> (SELECT embedding FROM t))::numeric,4) AS dist
FROM disaster_alert a
JOIN disaster_alert_region r ON r.disaster_alert_id = a.disaster_alert_id
JOIN disaster_events e ON e.id = a.event_id
WHERE e.is_broadcast = false
  AND left(r.legal_district_code,5) IN (SELECT c FROM s)
  AND a.created_at < (SELECT created_at FROM t)
  AND a.embedding IS NOT NULL
  -- 이벤트의 마지막 알림(판정 시점 이전)이 168h 안인가 = 168h 안에 알림이 하나라도 있는가
  AND EXISTS (SELECT 1 FROM disaster_alert a2
              WHERE a2.event_id = a.event_id
                AND a2.created_at < (SELECT created_at FROM t)
                AND a2.created_at > (SELECT created_at FROM t) - interval '168 hours')
GROUP BY a.event_id ORDER BY dist LIMIT 3;
```

정답 이벤트가 이 SQL 의 상위 3개(실제 검색의 상위 3개와 같은 범위)에 있어도 **이것만으로 판정 단계 실패를 확정하지 마라** — 이 결과는 판정 당시의 후보를 증명하지 못한다. 재클러스터링 로그로 정답 이벤트가 실제 검색 후보였음을 확인한 경우에만 검색이 아니라 판정(임계값·LLM 폴백·가드)에서 막힌 것으로 본다. 그 다음은 코드를 읽어야 한다 — 기록이 있어도 "무엇을 봤는가"까지만 알 수 있고 "왜 그 가드에 걸렸는가"는 코드에만 있다(2026-11-07 거제 화재 사례에서 실제로 그랬다).

- 평가 사본에서 재클러스터링(백필)할 때는 먼저 알림의 이벤트 배정(`disaster_alert` 의 `event_` 컬럼 5개)을 `NULL` 로 지우고, `disaster_events` 를 참조하는 `disaster_event_translation`·`event_region_impact`·`region_risk_index` 를 `TRUNCATE` 한 뒤, `disaster_events` 를 `DELETE` 한다. `disaster_alert.event_id` 가 `disaster_events` 를 참조해 `disaster_events` 는 `TRUNCATE` 할 수 없다(`TRUNCATE … CASCADE` 는 `disaster_alert` 까지 비우므로 절대 쓰지 않는다). 위험도 기능은 2026-11-05 에 삭제됐지만 `event_region_impact`·`region_risk_index` 테이블과 외래 키는 남아 있어 지금도 비워야 한다. 자동으로 지우지 않는다. 명령은 `EventClusteringBackfillTool` javadoc 의 권장 절차·`backend/evaluation/README.md` 와 같다.

## 이 도구가 하지 않는 것
- **왜 놓쳤는지(검색 단계인지 판정 단계인지) 계산하지 않는다.** 어느 단계가 막혔는지는 필요할 때 별도로 조사한다.
- **클러스터링을 다시 하지 않는다.** DB 에 저장된 이벤트 배정을 읽을 뿐이다. 클러스터링 코드를 바꿨다면 먼저 재클러스터링(백필)으로 새 스냅샷을 만든 뒤 그 DB 를 평가해야 바뀐 결과가 나온다. 평가와 재클러스터링은 일부러 분리했다.

## 데이터셋
`backend/evaluation/datasets/`의 JSON 배열. 항목마다 `q`(문항 번호), `label`(SAME·DIFF·UNSURE), `relation`, `gap`, `a`·`b`(각각 `id`, `at`, `type`, `region`, `message`)가 있다. 평가 계산에는 `a.id`·`b.id`·`label` 만 쓰고 나머지는 사람이 판정을 대조하려고 둔 필드다. 데이터셋 이름은 파일명에서 확장자를 뗀 것이다.
- `cluster-eval-2026-11.json`: **유일한 평가 셋**(272쌍, 같은 사건 126 / 다른 사건 104 / 모르겠음 42). 2026-11-09 한 번의 라벨링으로 매긴 쌍만 담는다. 사본 `disaster_alert_eval_v5`(운영 분류값) 에서 잰다. 구성·기준은 `.rubric.md`
- 예전 셋(`cluster-eval-2026-10-incident`·`-test`, 개발용 `cluster-eval-2026-10`)은 모두 지웠다 — 기준이 바뀌기 전 라벨이라 섞이면 헷갈린다(경위는 `CLUSTERING_EVALUATION.md` 4절, 파일은 git 이력)

리포트를 볼 때는 전체 쌍 수 대비 계산에 쓰인 쌍 수("제외" 줄)를 함께 본다.

리포트는 `backend/evaluation/reports/` 에 둔다. 지금 기준점은 `2026-11_2026-11-11.md` 다. 그 전 리포트는 지운 예전 셋으로 잰 기록이라 이 셋과 직접 비교하지 않는다. 그중 `*_2026-10-19.md` 세 개가 이 도구로 잰 첫 기준점이었고, 그 전 리포트(`before.md`, `after_v0.md` 등)는 옛 형식이라 직접 비교하지 않는다.

## 실행
라벨은 JSON 파일에서 바로 읽는다(DB 적재 없음, `evaluation_label` 테이블도 쓰지 않는다). 평가용 DB 사본에서 `eval` 프로필로 실행한다(OpenAI 호출 없음, 운영 DB 에는 실행하지 않는다). `backend/` 에서 루트 `.env.dev` 를 불러온 뒤 실행한다.
```
set -a; . ../.env.dev; set +a
./gradlew bootRun --args='--spring.profiles.active=eval --spring.datasource.url=jdbc:postgresql://localhost:5432/disaster_alert_eval_v5 --server.port=0 --eval.labels=<라벨 JSON 경로> --eval.report=<리포트 경로>'
```
- `--spring.datasource.url`(사실상 필수): 평가 사본. 빼면 `.env.dev` 의 개발 DB 에 붙어 엉뚱한 배정을 읽는다. `--server.port=0` 은 실행 중인 다른 서버와 포트가 겹치지 않게 한다.
- `--eval.labels`(필수): 라벨 JSON 경로.
- `--eval.report`(선택): 마크다운 리포트 경로. 없으면 로그로만 출력한다.
- `--eval.bcubed`(선택): B-cubed 정답 JSON 경로(예: `backend/evaluation/datasets/bcubed-2026-05.labels.json`). 주면 리포트 맨 끝에 `## 알림 단위 점수` 절이 붙고, 안 주면 그 절이 없다. `unreviewed` 가 남았거나 형식이 틀리면 DB 를 건드리기 전에 즉시 실패한다. `--eval.labels` 는 이 옵션과 상관없이 계속 필수다.
- 리포트 머리에는 데이터셋 이름과 실행 시각만 적고, 끝나면 애플리케이션이 종료된다.
- 라벨 파일 형식 오류는 즉시 실패한다. 항목 검증 오류(숫자가 아니거나 없는 id, 같은 id, 알 수 없는 label, (a,b)/(b,a) 중복)는 "N번째 항목"을 함께 알려 주고, JSON 구문이 깨졌거나 최상위가 배열이 아니면 항목 번호 없이 알려 준다.
