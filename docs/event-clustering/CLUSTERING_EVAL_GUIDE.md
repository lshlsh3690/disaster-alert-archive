# 클러스터링 평가 읽는 법

이벤트 클러스터링이 잘 묶었는지를 사람이 라벨한 알림 쌍으로 재는 도구의 설명서다. 계산은 일부러 단순하게 두었다.

## 하는 일 한 줄
사람이 라벨한 **알림 쌍**마다 "두 알림이 **같은 이벤트**에 들어 있는가"만 본다.

## 쌍 하나가 어떻게 세어지나
| 사람의 라벨 | 시스템 | 세는 이름 |
|---|---|---|
| 같은 사건 | 같은 이벤트 | **맞게 묶음** |
| 같은 사건 | 다른 이벤트 | **놓침** |
| 다른 사건 | 같은 이벤트 | **잘못 묶음** |
| 다른 사건 | 다른 이벤트 | 세지 않는다 |

## 지표 두 개
- **과소병합율** = 놓침 ÷ (맞게 묶음 + 놓침). 사람이 같은 사건이라 한 쌍 중 못 묶은 비율. 낮을수록 좋다.
- **과병합율** = 잘못 묶음 ÷ (맞게 묶음 + 잘못 묶음). 시스템이 묶은 쌍 중 사람이 다른 사건이라 한 비율. 낮을수록 좋다.

### 예시 (쌍 6개)
| 쌍 | 사람 | 시스템 | 세는 이름 |
|---|---|---|---|
| 1 | 같은 사건 | 같은 이벤트 | 맞게 묶음 |
| 2 | 같은 사건 | 같은 이벤트 | 맞게 묶음 |
| 3 | 같은 사건 | 다른 이벤트 | 놓침 |
| 4 | 같은 사건 | 다른 이벤트 | 놓침 |
| 5 | 다른 사건 | 같은 이벤트 | 잘못 묶음 |
| 6 | 다른 사건 | 다른 이벤트 | (세지 않음) |

- 과소병합율 = 2 ÷ (2 + 2) = 50%. 같은 사건 4쌍 중 2쌍을 놓쳤다.
- 과병합율 = 1 ÷ (2 + 1) = 33.3%. 묶은 3쌍 중 1쌍이 잘못됐다.

## 평가에서 빠지는 쌍
- **모르겠음**: 라벨이 "모르겠음"인 쌍.
- **이벤트 미배정**: 두 알림 중 하나라도 이벤트에 들어 있지 않은 쌍(비사건으로 분류되어 클러스터링에서 빠졌거나 처리되지 않은 알림). 정답을 가릴 수 없어서 빼고 건수만 센다.
- 두 건수는 리포트에 따로 적힌다. 둘 다 해당하면 모르겠음으로 센다.

## 리포트
```
## 요약
- 같은 사건 60쌍 중 38쌍 묶음, 22쌍 놓침 → 과소병합율 36.7%
- 묶은 40쌍 중 38쌍 맞음, 2쌍 잘못 묶음 → 과병합율 5.0%
- 제외: 모르겠음 6쌍, 이벤트 미배정 0쌍
## 놓친 쌍 / 잘못 묶은 쌍
| alertA | alertB | 유형 | 같은 시군구 | 간격(시간) | 본문 거리 | 종류 |
```
(위 숫자는 설명용 예시다.) 놓친 쌍과 잘못 묶은 쌍에는 **이유를 계산하지 않고 사실만** 적는다.
- 유형: 두 알림의 재난 유형(다르면 "A/B").
- 같은 시군구: 두 알림이 시군구(법정동 코드 앞 5자리)를 하나라도 공유하면 "예".
- 간격(시간): 두 알림 발송 시각의 차.
- 본문 거리: 두 알림 본문 임베딩의 코사인 거리(작을수록 비슷, 병합 기준은 0.15 이하). 임베딩이 없으면 "-".
- 종류: `놓침`(같은 사건인데 안 묶음) 또는 `잘못 묶음`(다른 사건인데 묶음). 2026-11-07 에 추가한 칸이라 그 전 리포트에는 없다.

## 이전 대비 — 튜닝 전후는 이걸 먼저 본다
**두 비율의 변화로 개선 여부를 판단하지 않는다.** 사건 셋은 같은 사건이 60쌍뿐이라 과소병합율의 95% 신뢰구간이 ±12%p 수준이고, 실제로 48.3% → 36.7% 변화 뒤에 **퇴행 2건이 가려져 있었다**. 같은 셋을 반복해 쓰므로 쌍이 짝지어져 있고, 짝지은 비교가 비율 비교보다 훨씬 민감하다(근거: `CLUSTERING_EVALUATION.md` 8절).

`--eval.baseline` 에 **이전 리포트 파일 경로**를 주면 리포트 끝에 `## 이전 대비` 절이 붙는다. 안 주면 이 절 자체가 없다(빈 절을 쓰면 "퇴행 없음"으로 잘못 읽히기 때문).

```
## 이전 대비
- 고쳐짐 9쌍, 새로 틀림 2쌍, 종류 바뀜 0쌍

### 새로 틀린 쌍
| alertA | alertB | 유형 | 같은 시군구 | 간격(시간) | 본문 거리 | 종류 |
| 24650 | 27626 | 산불 | 예 | 36 | 0.191 | 놓침 |

### 고쳐진 쌍
- 101 ↔ 102
```

읽는 순서:
1. **새로 틀린 쌍** — 이번 변경이 망가뜨린 것. 1차 산출물이고, 한 건이라도 있으면 비율이 좋아졌어도 그 원인을 먼저 본다. 사실 칸(유형·간격·거리)은 이번 실행에서 가져온다.
2. **고쳐진 쌍** — 이번 변경이 고친 것. id 둘만 적는다.
3. **종류 바뀜** — 같은 쌍이 `놓침` ↔ `잘못 묶음` 으로 뒤집힌 경우. 이전 리포트에 종류 칸이 없으면(2026-11-07 이전 리포트) 추측하지 않고 세지 않는다.
4. 두 비율은 그 다음에 2차로 읽는다.

쌍은 **순서 무관**으로 같다고 본다 — 이전에 `(a,b)`, 이번에 `(b,a)` 로 적혔어도 같은 쌍이다.

주의: 기준선 파일에 `## 놓친 쌍 / 잘못 묶은 쌍` 절 제목이 없으면(평가 리포트가 아닌 파일) `BaselineReportParser.parse` 가 `IllegalArgumentException` 을 던져 **즉시 실패한다.** 조용히 "이전에 틀린 쌍 0개"로 읽혀 이번 틀린 쌍 전부가 "새로 틀림"으로 나오는 경우는 둘뿐이다: (a) 제목은 있고 표가 빈 정상 기준선, (b) 현재 평가와 **다른 데이터셋**의 기준선(이번 범위에서는 막지 않는다). 고쳐짐 0 / 새로 틀림이 이번 틀린 쌍 수와 같으면 (b) 를 의심해 기준선 경로·데이터셋부터 확인하라.

## 틀린 쌍을 들여다보는 법
리포트의 틀린 쌍은 사실만 적혀 있고 **왜 그렇게 됐는지는 적히지 않는다.** 원인은 사람이 따로 찾는다.

판정 순간을 기록하던 `clustering_trace` 테이블은 **2026-11-08 에 들어냈다**(경위는 `CLUSTERING_EVALUATION.md` 9절). 그래서 지금 쓸 수 있는 수단은 둘뿐이다.

1. **재클러스터링 로그** — 알림마다 탄 경로, 후보 이벤트와 거리(`event=… dist=…`), 병합 결과가 찍힌다. 재클러스터링할 때 로그를 파일로 남겨 두면 그 실행에 한해 판정을 되짚을 수 있다.
2. **후보 검색을 SQL 로 재현** — 나중에 들어온 알림 기준으로 "같은 시군구 + 후보 윈도우(168h) 안 이벤트"를 거리순으로 다시 뽑아 본다. 그 순간 실제로 본 후보가 아니라 **지금 데이터로 다시 계산한 값**이라는 한계가 있다.

```sql
-- 먼저 들어온 알림이 속한 정답 이벤트
SELECT event_id FROM event_alert_mapping WHERE alert_id = <먼저 알림 id>;

-- 나중 알림 기준으로 같은 시군구·168h 안 후보를 거리순으로 재현
WITH t AS (SELECT embedding, created_at FROM disaster_alert WHERE disaster_alert_id = <나중 알림 id>),
     s AS (SELECT DISTINCT left(legal_district_code,5) c FROM disaster_alert_region WHERE disaster_alert_id = <나중 알림 id>)
SELECT m.event_id, round(min(a.embedding <=> (SELECT embedding FROM t))::numeric,4) AS dist
FROM event_alert_mapping m
JOIN disaster_alert a ON a.disaster_alert_id = m.alert_id
JOIN disaster_alert_region r ON r.disaster_alert_id = a.disaster_alert_id
WHERE left(r.legal_district_code,5) IN (SELECT c FROM s)
  AND a.created_at < (SELECT created_at FROM t)
  AND a.created_at >= (SELECT created_at FROM t) - interval '168 hours'
  AND a.embedding IS NOT NULL
GROUP BY m.event_id ORDER BY dist LIMIT 5;
```

정답 이벤트가 **거리 상위에 있는데도 안 묶였다면** 검색이 아니라 판정(임계값·LLM 폴백·가드)에서 막힌 것이다. 그 다음은 코드를 읽어야 한다 — 기록이 있어도 "무엇을 봤는가"까지만 알 수 있고 "왜 그 가드에 걸렸는가"는 코드에만 있다(2026-11-07 거제 화재 사례에서 실제로 그랬다).

- 평가 사본에서 재클러스터링(백필)할 때는 `event_alert_mapping`, `disaster_event_translation`, `event_region_impact`, `region_risk_index`, `disaster_events` 를 **한 번의 `TRUNCATE` 명령**으로 함께 비운 뒤 돌려야 한다. 앞의 세 표는 `disaster_events` 를 참조하는 외래 키가 있어 같은 명령에 넣지 않으면 `TRUNCATE` 가 실패한다. 위험도 기능은 2026-11-05 에 삭제됐지만 `event_region_impact`·`region_risk_index` 테이블과 외래 키는 남아 있어 지금도 비워야 한다. 자동으로 지우지 않는다. 명령은 `EventClusteringBackfillTool` javadoc 의 권장 절차와 같다: `TRUNCATE event_alert_mapping, disaster_event_translation, event_region_impact, region_risk_index, disaster_events RESTART IDENTITY;`

## 이 도구가 하지 않는 것
- **왜 놓쳤는지(검색 단계인지 판정 단계인지) 계산하지 않는다.** 어느 단계가 막혔는지는 필요할 때 별도로 조사한다.
- **클러스터링을 다시 하지 않는다.** DB 에 저장된 이벤트 배정을 읽을 뿐이다. 클러스터링 코드를 바꿨다면 먼저 재클러스터링(백필)으로 새 스냅샷을 만든 뒤 그 DB 를 평가해야 바뀐 결과가 나온다. 평가와 재클러스터링은 일부러 분리했다.

## 데이터셋
`backend/evaluation/datasets/`의 CSV(`alert_a_id,alert_b_id,label,stratum,sub_type`). `label`은 SAME·DIFF·UNSURE 이고 `stratum`·`sub_type`은 형식 호환용이라 읽고 버린다(평가 계산에 쓰지 않는다). 데이터셋 이름은 CSV 파일명에서 확장자를 뗀 것이다.
- `cluster-eval-2026-10-incident.csv`: 사건 셋(두 알림 모두 사건으로 분류된 쌍, 96쌍). 튜닝 전후 비교의 기준 셋
- `cluster-eval-2026-10-test.csv`: 홀드아웃 셋(규칙 튜닝에 쓰지 않은 셋, 요청할 때만 돌린다). 비사건 제외 후 100쌍 중 80쌍이 미배정으로 빠져 19쌍만 계산된다
- 개발용 셋 `cluster-eval-2026-10.csv` 는 2026-10-24 삭제했다(경위는 `CLUSTERING_EVALUATION.md` 4절)

리포트를 볼 때는 전체 쌍 수 대비 계산에 쓰인 쌍 수("제외" 줄)를 함께 본다.

리포트는 `backend/evaluation/reports/` 에 둔다. `*_2026-10-19.md` 세 개가 이 도구로 잰 기준점이고, 그 전 리포트(`before.md`, `after_v0.md` 등)는 옛 형식이라 직접 비교하지 않는다.

## 실행
라벨은 CSV 에서 바로 읽는다(DB 적재 없음, `evaluation_label` 테이블도 쓰지 않는다). 평가용 DB 사본에서 `eval` 프로필로 실행한다(OpenAI 호출 없음, 운영 DB 에는 실행하지 않는다).
```
./gradlew bootRun --args='--spring.profiles.active=eval --eval.labels=<CSV 경로> --eval.report=<리포트 경로> --eval.baseline=<이전 리포트 경로>'
```
- `--eval.labels`(필수): 라벨 CSV 경로.
- `--eval.report`(선택): 마크다운 리포트 경로. 없으면 로그로만 출력한다.
- `--eval.baseline`(선택): 비교할 **이전 리포트** 경로(예: `backend/evaluation/reports/incident_2026-11-07.md`). 주면 `## 이전 대비` 절이 붙고, 안 주면 그 절이 없다. 파일이 없거나 `## 놓친 쌍 / 잘못 묶은 쌍` 절 제목이 없으면(`IllegalArgumentException`) DB 를 건드리기 전에 즉시 실패한다. 읽는 법은 위 "이전 대비" 절.
- 리포트 머리에는 데이터셋 이름과 실행 시각만 적고, 끝나면 애플리케이션이 종료된다.
- CSV 형식 오류(헤더 불일치, 컬럼 수, 숫자 아님, 같은 id, 알 수 없는 label, (a,b)/(b,a) 중복)는 줄 번호와 함께 즉시 실패한다.
