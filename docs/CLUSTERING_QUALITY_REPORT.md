## 1. 평가 파이프라인과 단계 정의

클러스터링은 RAG가 아니지만 같은 틀로 쪼개서 평가하면 오류 원인을 분리할 수 있다.

| 단계 | RAG 대응 | 클러스터링에서의 의미 | 측정 방법 |
|---|---|---|---|
| 평가 데이터셋 | 평가 셋 구축 | 사람이 "같은 사건 / 다른 사건 / 모르겠음"을 라벨한 쌍 | 개발용 150쌍, 최종용 100쌍 |
| 추론 실행 | 추론 | 저장된 임베딩으로 재클러스터링(`recluster`)해 각 버전의 이벤트 배정을 얻음 | 버전별 평가 DB 사본 |
| **검색 (Retrieval)** | 검색 | 새 문자와 연관된 이벤트를 **후보로 선정**(같은 시군구 + 인접 시군구, 거리순 상위 3개) | **검색 실패**: 정답 이벤트가 후보에 없음 |
| **판정 (Generation 대응)** | 생성 | 후보와 **묶을지 말지 결정**(거리 임계값, 앵커링 규칙, LLM 폴백, 가드) | **판정 실패**: 후보에 있는데 안 묶음 / **과병합**: 다른 사건을 묶음 |
| **엔드투엔드** | 엔드투엔드 | 결과로 나온 **이벤트의 모양**(쪼개짐, 여러 시군구·긴 기간에 걸쳐 이어 붙음) | 쌍 정밀도·재현율 + 이벤트 구조 지표 |
| LLM-as-a-Judge | 판사 평가 | LLM이 사람 대신 쌍을 판정 | **미채택** (아래 6절) |
| 병목 진단·튜닝 | 병목 진단 | 오류를 검색/판정으로 분해해 개선 | 이 보고서의 2~4절 |

## 3. 단계별 개선량

### 3.1 검색 (Retrieval) — 검색 실패 13건 → 7건 (-46%)

| 개선 | 효과 |
|---|---|
| 에피소드형 유형(폭염·한파·대설·강풍·가축질병)을 "유형+시군구" 앵커로 직접 묶음 | 후보 검색을 아예 거치지 않게 되어 검색 실패 13 → 9 (-4건) |
| 사고성 유형에 **인접 시군구 후보** 추가 (+ 후보 이벤트 가드, 이벤트 나이 상한 72시간) | 같은 사고가 이웃 시군구로 각각 발송된 쌍이 후보에 오름. 검색 실패 9 → 7 (-2건), 재현율 +1.8%p |

최종용 100쌍에서는 검색 실패 9 → 4 (-56%).

남은 검색 실패 7건은 후보 3개 안에 못 든 쌍이다. 키워드 하이브리드 검색이 다음 후보지만 구현하지 않았다.

### 3.2 판정 (Generation 대응) — 판정 실패 29건 → 10건 (-66%)

| 개선 | 효과 |
|---|---|
| 에피소드형 앵커링(안내와 특보를 같은 이벤트로) + 임계값 완화 | 판정 실패 29 → 13 (-16건), **재현율 +18.3%p**. 이번 개선의 가장 큰 부분(전체 개선의 약 80%) |
| 안내성 분리(기타 물놀이 안내) | 판정 실패 13 → 12 (-1건) |
| **LLM 폴백 켬** (같은 사고의 다른 단계 알림: 통제 → 해제, 진화 중 → 진압 완료 등을 합침) | 개발용 판정 실패 12 → 10, 재현율 +1.8%p. 최종용에서는 판정 실패 21 → 5 (-76%), 재현율 0.627 → 0.866 (+23.9%p) |

LLM 폴백으로 병합된 알림은 재클러스터링 전체에서 399건이다. 폴백은 사고성 유형의 같은 시군구 borderline 후보에만 호출된다.

### 3.3 엔드투엔드 (이벤트 구조)

쌍 지표로는 안 잡히는 문제를 이벤트 구조 지표로 측정했다.

| 지표 | V0 | V4 | V7 | V10 | V11 |
|---|---|---|---|---|---|
| 전체 이벤트 수 | 9,697 | 5,857 | 5,805 | 5,787 | 5,388 |
| 6곳 이상에 걸친 일반(비광역) 이벤트 | 108 | 58 | 58 | 55 | 51 |
| 일반 이벤트가 걸친 시군구 최대 | 47 | 29 | 29 | 12 | 12 |
| 안내 이벤트가 걸친 시군구 최대 | 29 | 29 | 29 | 1 | 1 |
| 2곳 이상에 걸친 안내 이벤트 | 19 | 19 | 19 | 0 | 0 |
| 일반 이벤트 최대 알림 수 | 360 | 360 | 360 | 145 | 145 |

- 평가 DB에서 확인된 가장 큰 문제는 "경상북도 포항시 남구 산불예방안내" 이벤트 하나가 **알림 360건 · 148일 · 29개 시군구**에 걸쳐 있던 것이다. 다지역 안내문이 시군구 교집합으로 이웃 시군구 안내 이벤트를 이어 붙이는 구조 때문이었다.
- 같은 방식으로 `기타` 물놀이 안내문이 7개 시군구·44일짜리 이벤트가 된 사례도 있었다(인접 병합이 마지막 알림 기준 윈도우를 계속 밀어서 생김 → 이벤트 첫 알림 72시간 상한으로 해결).
- 이 문제들은 쌍 라벨에 해당 쌍이 없어서 정밀도·재현율에는 전혀 잡히지 않았고, 이벤트 구조를 SQL로 직접 보고서야 발견됐다. **쌍 지표만으로는 부족하다**는 것이 이번 작업의 교훈 중 하나다.
- 개선 방법: 다지역 안내를 시도(전국급이면 전국) + 유형 키의 "안내 광역 이벤트"로 보내고, 시군구 1개 안내는 시군구별 안내 이벤트로 이어 붙임(되풀이 안내는 같은 사건).
- 개발용 재현율에는 +0.9%p만 기여했다. 이 단계의 가치는 이벤트 구조의 정상화에 있다.

## 4. 최종 개선량 요약

개발용 150쌍 재현율 기준 단계별 기여 (합계 +22.9%p):

| 단계 | 재현율 변화 | 전체 개선 중 비중 |
|---|---|---|
| 판정 규칙 (에피소드형 앵커링 + 임계값 완화, V0 → V4) | +18.3%p | 약 80% |
| 검색 (인접 시군구 후보, V4 → V6) | +1.8%p | 약 8% |
| 엔드투엔드 (안내성 분리, V6 → V10) | +0.9%p | 약 4% |
| 판정 (LLM 폴백, V10 → V11) | +1.8%p | 약 8% |
| **합계 (V0 → V11)** | **+22.9%p (0.615 → 0.844, 상대 +37%)** | 100% |

- 오류 건수: 검색 실패 -46% (13 → 7), 판정 실패 -66% (29 → 10), 과병합 0건 유지.
- 정밀도는 개발용에서 1.000 유지, 최종용에서 0.964 → 0.983.
- 이벤트 수 -44%, 이벤트가 걸친 시군구 최대 -74%.

모집단 수준 추정(최종용 표본을 층 크기로 가중, 가정이 많아 거친 값):
- 정밀도 약 97% 안팎, 재현율 LLM 꺼짐 약 85%, **LLM 켬 약 90% 이상 (대략 80~95%)**.

## 5. 한계와 주의

- **라벨러가 1명**이고 부정 예시가 적다(개발용 38쌍). 라벨 일치도(kappa)는 재지 못했다.
- **최종용 100쌍은 V8 결과에서 뽑은 표본**이다. 정밀도 표본 40쌍이 V8이 합친 쌍이라 V10 이후 버전에 유리하고, V0에 불리한 구조다. V0 대비 개선 폭은 개발용 150쌍 기준으로 읽어야 한다. 표본이 어려운 쌍을 많이 포함해서 재현율이 모집단보다 낮게 나오는 점도 있다.
- 모집단 수준 추정은 표본이 작아 오차가 크다(층별 13~40쌍).
- LLM 폴백을 켠 측정은 **단일 실행**이며 LLM 응답이 결정적이지 않아 다시 돌리면 몇 쌍은 달라질 수 있다(프롬프트 규칙 실험에서 실제로 1쌍이 바뀜).
- LLM 폴백이 별개의 사고를 합친 사례가 1건 있었다(김해시 진례면 ↔ 생림면 공장 화재, 사람 라벨 다른 사건). 최종용 표본 기준 LLM 병합 정밀도 약 94% (15/16).
- 이미 운영 DB에 있는 큰 안내 이벤트는 이번 변경으로 정리되지 않는다. 앞으로 들어오는 알림의 분류만 바뀐다.
- 새 SQL 조건은 Mockito 테스트로 검증할 수 없다. 첫 구현은 단위 테스트가 모두 통과했는데도 결함이 있었고(안내 광역 이벤트가 새 다리가 됨), 실제 DB 재클러스터링의 이벤트 구조 점검에서 발견했다.

## 6. LLM-as-a-Judge: 검토 후 미채택

- 계획: 사람 라벨 147쌍으로 gpt-4o 판사의 일치율을 먼저 검증하고, 통과하면 무작위 500쌍을 판정시켜 평가 셋을 늘린다.
- 부품(프롬프트, 응답 파서, 비용 추정·예산, 쌍 판정 서비스 + 캐시, 일치율·kappa 계산)을 만들었고 실제 호출 전에 중단했다. OpenAI 비용은 **0원**이다.
- 중단 이유: (1) 이미 사람이 라벨한 쌍이 있어 판사는 일회성 검증용 성격이 강하다. (2) 사람 라벨이 최종 근거라 신뢰도가 높다. (3) 잔고 대비 이해·유지 비용이 크다.
- 대신 평가 셋 보강은 **사람이 직접 라벨한 최종용 표본 100쌍**으로 했다. 시스템 판정을 숨긴 퀴즈를 만들어 직접 판정했고 판정 기준을 일관되게 적용했다.
- 코드는 저장소에 올리지 않고 삭제했다.

## 7. 비용 (LLM 폴백을 켠 측정)

- 재클러스터링 LLM 호출 약 1,400회 추정 × `gpt-4o-mini` (입력 $0.15 / 출력 $0.60, 100만 토큰당) → 약 $0.25 (최대 $1.3).
- 실제 지출은 OpenAI 사용량 대시보드로 별도 확인 필요.
- 운영에서는 폴백이 기본으로 켜져 있어 알림당 LLM 호출이 한 번 발생할 수 있다(사고성 borderline 후보가 있을 때만).

## 8. 후속 작업

- LLM 폴백 프롬프트에 "발생 장소가 다르면 별개 사건" 규칙을 추가해 V12로 다시 측정했으나 **김해 사례의 과병합은 해소되지 않았다**(개발용 92/0/17/38 동일, 최종용 58/1/9/31 → 59/1/8/31, LLM 병합 399 → 371건). 달라진 1쌍은 LLM 응답의 변동으로 보여 이 규칙의 효과는 확인되지 않았고, 반영하지 않았다. 과병합을 줄이려면 프롬프트만으로는 부족하므로 병합 전 장소(읍면동·번지) 일치 검증 같은 결정적 가드를 별도로 검토한다.
- 검색 실패 7건: 키워드 하이브리드 검색 또는 후보 수 확대 검토.
- 실사건 산불이 안내로 오분류될 가능성에 대한 보호 테스트, `dominantSidoPrefix` 동률 시 비결정성 정리.
- 운영 DB의 기존 큰 안내 이벤트 정리(백필) 여부 결정.
- 평가 셋 보강: 무작위 표본의 추가 확대, 두 번째 라벨러.
