# 결정 기록: 불일치 쌍 사람 라벨링

## R1. 라벨의 키 — 날짜 없이 두 알림 쌍

- **결정**: `(alert_a, alert_b)`(작은 id 가 a) UNIQUE. 날짜·채점 쌍 id 를 키로 쓰지 않는다.
- **근거**: 사람 라벨은 "두 알림이 같은 사건인가"에 대한 판단이라 날짜와 무관하다. 채점 쌍은 X(그날 알림)와 168시간 안의 Y 로 만들어 보통 한 번만 나오지만, 같은 날 재채점하면 채점 쌍 행이 다시 만들어질 수 있다. 쌍으로 키를 잡으면 라벨이 재채점에도 살아남는다.
- **검토한 대안**: 채점 쌍 id 에 외래 키 — 재채점 때 라벨이 사라지거나 외래 키 때문에 재채점이 막힌다. 탈락.

## R2. 외래 키를 걸지 않는다

- **결정**: `clustering_pair_label` 은 채점 쌍·알림·회원에 외래 키를 걸지 않는다.
- **근거**: `clustering_daily_score_pair` 의 `event_a/event_b` 와 같은 방침(당시 상태를 남기고 다른 작업을 막지 않음). 알림은 지우지 않으므로 고아 행이 생길 일이 거의 없고, 생겨도 집계는 "지금 불일치 쌍과 이어지는 라벨"만 센다.
- **검토한 대안**: 알림 외래 키 — 알림 백필·이관(법정동 재발급 등) 때 제약이 걸릴 수 있어 탈락.

## R3. 덮어쓰기 + 처음/마지막 작성자, 이력 테이블 없음

- **결정**: 한 쌍에 라벨 한 줄. 고치면 덮어쓰고 `created_by/created_at`(처음), `updated_by/updated_at`(마지막)을 둔다.
- **근거**: 라벨링하는 사람이 1~2명이고, spec 은 "누가 마지막으로 바꿨는지"만 요구한다. 이력 테이블은 지금 쓸 곳이 없다(헌법 I).
- **검토한 대안**: 라벨 변경 이력 테이블 — 평가자 간 일치도 같은 기능이 생길 때 추가. 지금은 탈락.

## R4. 동시 첫 저장 — UNIQUE 충돌 시 다시 찾아 고친다

- **결정**: service 가 쌍을 찾고 없으면 새로 저장한다. 두 요청이 동시에 처음 저장하다 UNIQUE 에 걸리면, 걸린 쪽이 다시 찾아 `relabel` 한다(나중 저장이 남음).
- **근거**: 엔티티 메서드로 상태를 바꾸는 팀 컨벤션을 지키면서, spec 의 "나중 저장이 남는다"를 만족한다. 관리자 1~2명이라 충돌 자체가 드물다.
- **검토한 대안**: 네이티브 `INSERT ... ON CONFLICT DO UPDATE` — 한 줄로 끝나지만 엔티티 메서드를 우회한다. 탈락.

## R5. 누가 틀렸는지 판정 규칙

- **결정**: 정답 = 사람 라벨. 판사가 맞음 ⇔ `judge_verdict == label`. 시스템이 맞음 ⇔ `system_same_event == (label == SAME)`. 불일치 쌍(과병합 = 시스템 묶음 + 판사 DIFF, 과소병합 = 시스템 분리 + 판사 SAME)에서는 둘 중 정확히 하나만 맞으므로 `WrongSide` = JUDGE 또는 SYSTEM. UNSURE 는 판정 없음.
- **근거**: 불일치 쌍의 정의(006, V139)에서 판사와 시스템의 답이 반대라 라벨이 SAME/DIFF 면 한쪽만 맞는다. 규칙이 단순해 순수 클래스 단위 테스트로 고정하기 좋다.
- **검토한 대안**: 과병합/과소병합 종류로 바로 판정 — 결과는 같지만 `system_same_event` 와 판사 판정에서 계산하는 편이 정의를 그대로 따른다.

## R6. 판사 버전별 집계, 지금 불일치인 쌍만

- **결정**: 쌍의 판사 버전 = 그 쌍을 채점한 날(`score_date`)의 `clustering_daily_score.judge_version`. 집계는 지금 `disagreement IS NOT NULL` 인 채점 쌍과 이어지는 라벨만 센다.
- **근거**: 판사 버전마다 틀리는 방향이 달라(v1 은 잘게, v2 는 크게 묶는 쪽) 섞으면 해석이 안 된다(spec FR-008). 재채점으로 불일치가 아니게 된 쌍은 그 판사가 이제 시스템과 같은 답을 낸 것이라 어려운 쌍 성적에 넣지 않는다.
- **검토한 대안**: 전체 합산 — 버전이 바뀌는 지점이 묻혀 탈락.

## R7. 기준 시점 상수 한 곳

- **결정**: 순수 클래스 `ClusteringCriteria.VERSION_DATE = 2026-11-13`. 라벨 저장 때 서버가 이 값을 붙인다. `CLUSTERING_CRITERIA.md` 머리에 "기준을 바꾸면 이 상수도 바꾼다"는 안내를 둔다.
- **근거**: 사람이 입력하지 않게 해 실수를 없앤다(spec FR-004). 기준 문서의 마지막 경계 사례 변경일이 2026-11-13(G 에 옛 H 합침)이다.
- **검토한 대안**: application.yml 설정 — 기준 문서는 저장소에 있고 운영 환경마다 다를 이유가 없어 탈락.

## R8. 파일 내보내기 대신 평가 도구가 DB 라벨을 읽는다 (2026-11-18 변경)

- **결정**: 회귀 셋을 JSON 파일로 내보내지 않는다. 평가 도구(`EvaluationRunTool`)에 `--eval.pair-labels-as-of=<시각>` 옵션을 더해 평가 사본의 `clustering_pair_label` 을 바로 읽는다.
- **근거**: 사용자 결정("라벨링 값을 DB 에 저장해서 계속 재사용하는 게 낫다, json 보단"). 라벨의 원본을 DB 한 곳으로 두면 고친 라벨이 다음 평가에 바로 반영되고, 파일을 내려받아 저장소에 넣는 수작업과 사본이 어긋나는 일이 없다. 평가 사본은 운영 덤프로 만들어 라벨 테이블이 함께 들어온다.
- **검토한 대안**: 처음 설계(내보내기 API + 버튼 + `LabelJson` 형식 파일) — 사본이 생기고 수작업이 필요해 탈락. 272쌍까지 DB 로 옮기기 — 판사 측정 기준이라 고정돼야 하고 공개 저장소에 두기로 한 결정이 있어 이번 범위에서 뺌.

## R9. 저장(쓰기) service 를 조회 service 와 나눈다

- **결정**: 라벨 저장은 새 `ClusteringPairLabelService`, 조회·성적은 008 의 `ClusteringDashboardService`(readOnly) 에 둔다.
- **근거**: 008 조회 service 가 클래스 단위 `@Transactional(readOnly = true)` 라 쓰기를 섞으면 메서드마다 예외를 둬야 한다. 쓰기는 한 곳에 모아 권한·검증을 보기 쉽게 한다.

## R11. DB 라벨 평가의 재현성 — 기준 시각 + 정렬, 이력은 두지 않음

- **결정**: 평가 때 기준 시각을 받아 `updated_at ≤ 기준 시각` 인 라벨만 쓰고 `(alert_a, alert_b)` 순으로 정렬한다(`PairLabelSnapshot`). 리포트에 기준 시각·라벨 수를 적는다. 라벨 이력 테이블은 만들지 않는다.
- **근거**: 튜닝 전후 비교는 같은 라벨로 돌아야 한다. 기준 시각을 고정하면 그사이 새로 매긴 라벨이 섞이지 않고, 정렬로 틀린 쌍 표 순서가 같아진다(006 FR-013).
- **받아들인 한계**: 덮어쓰기 구조라 기준 시각 뒤에 고친 라벨은 옛 값으로 돌아가지 않고 빠진다. 라벨링하는 사람이 1~2명이고 고치는 일이 드물어 받아들인다. 리포트의 라벨 수가 이전과 다르면 알아볼 수 있다.
- **검토한 대안**: 라벨 변경 이력 테이블로 시점 복원 — 정확하지만 지금은 과하다(R3). 고칠 일이 잦아지면 그때 추가.

## R10. 저장할 수 있는 쌍 — 불일치로 기록된 쌍만

- **결정**: 라벨 저장 요청의 쌍이 `clustering_daily_score_pair` 에 불일치로 한 번이라도 기록돼 있지 않으면 404(`CLUSTERING_PAIR_NOT_FOUND`).
- **근거**: 이 기능의 대상은 불일치 쌍뿐이다(spec 가정). 아무 쌍이나 저장되면 어려운 쌍 성적과 회귀 셋의 의미가 흐려진다.
