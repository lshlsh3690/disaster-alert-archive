# 기능 명세: 판사 일치율 측정 결과를 DB 에 두고 현재 라벨로 계산한다

**기능 브랜치**: `feature/judge-agreement-db`

**생성일**: 2026-11-25

**상태**: Draft

**입력**: 사용자 설명: "라벨 데이터가 DB 에 있으니 판사 모델 결과도 DB 에 저장한다. 상수(JudgeVersionCatalog 의 일치율)가 아니라 테이블을 만들어 판사 측정 결과를 DB 에 넣는다. 011(보류)에서 측정 테이블 두 개(judge_agreement_run, judge_agreement_run_pair)만 떼어 쓴다. v2 쌍별 판정은 11-18 리포트에서 복원하고(재측정 없음), v1 은 합계만 옮긴다."

## 이 명세의 범위와 다른 문서와의 관계

- 판사(LLM as a judge)와 일일 채점 전반은 [`../006-clustering-evaluation/spec.md`](../006-clustering-evaluation/spec.md)·[`plan.md`](../006-clustering-evaluation/plan.md), 화면은 [`../008-clustering-admin-dashboard/spec.md`](../008-clustering-admin-dashboard/spec.md)(FR-004 일치율 표시, FR-010 판사 버전 이력)가 다룬다. 이 명세는 그중 **판사 일치율이 어디에 있고 어떻게 계산되는가**만 바꾼다.
- 보류된 [`../011-judge-improvement-loop/`](../011-judge-improvement-loop/)(미커밋)의 측정 두 테이블 설계와 v2 판정 복원 방법(research R4)을 가져온다. 011 의 나머지(판사 지시문의 DB 이관, 운영 판사 전환 기록, 개선안 초안, 화면의 재측정 버튼, 272쌍 전용 테이블)는 가져오지 않는다(2026-11-25 사용자 결정).
- 272쌍 사람 라벨은 이미 DB(`evaluation_pair_label`, 셋 이름 `cluster-eval-2026-11`)에 있고 관리자 화면에서 고친다. 평가 도구가 라벨 JSON 파일을 읽지 않게 한 PR #358 이 머지된 뒤 구현한다.

## 왜 바꾸나

- 판사 버전별 일치율(v2: 같은 사건 127/141, 다른 사건 74/81)이 코드 상수로 손으로 적혀 있다. 근거는 측정 리포트(마크다운)뿐이다.
- 라벨을 관리자 화면에서 고쳐도 일치율은 바뀌지 않는다. 2026-11-17 에는 측정 뒤 라벨을 두 번 고쳐 v1 값을 손으로 다시 세어 코드를 고쳤다.
- 판사의 판정은 라벨과 무관하다. 쌍별 판정을 남겨 두면 라벨이 바뀔 때 판사를 다시 부르지 않고(무료로) 일치율을 다시 계산할 수 있다.

## 사용자 시나리오 및 테스트 *(필수)*

### 사용자 스토리 1 - 판사 일치율이 DB 의 측정 기록에서 나온다 (우선순위: P1)

관리자는 대시보드의 판사 버전 이력과 일일 채점 표에서 판사 일치율을 본다. 이 값은 코드 상수가 아니라 DB 에 저장된 측정 기록(쌍별 판정)과 현재 사람 라벨을 맞대어 계산한 값이다. 운영 일일 채점은 채점하는 순간의 이 값을 그날 기록에 복사해 둔다.

**우선순위 이유**: 나머지 두 스토리의 바탕이다. 이것만으로도 "일치율의 근거가 마크다운 파일과 코드 상수뿐"인 상태가 끝난다.

**독립 테스트 방법**: v1·v2 측정 기록을 넣은 DB 로 대시보드 판사 버전 이력을 열어, 일치율이 지금 상수와 같은지(v2 127/141·74/81, v1 124/142·77/80) 확인한다.

**인수 시나리오**:

1. **Given** v2 측정 기록(쌍별 판정 225건)과 현재 272쌍 라벨이 DB 에 있음, **When** 관리자가 판사 버전 이력을 연다, **Then** v2 일치율이 같은 사건 127/141, 다른 사건 74/81 로 보인다.
2. **Given** v1 은 합계만 있는 측정 기록임, **When** 판사 버전 이력을 연다, **Then** v1 일치율이 124/142·77/80 으로 보이고, 이 값은 라벨이 바뀌어도 다시 계산되지 않는 값이라는 표시가 있다.
3. **Given** 현재 운영 판사 버전(v2)의 측정 기록이 있음, **When** 일일 채점이 하루를 채점한다, **Then** 그날 기록에 채점 순간의 v2 일치율이 저장되고, 이미 저장된 지난 날의 일치율은 바뀌지 않는다.

---

### 사용자 스토리 2 - 라벨을 고치면 판사를 다시 부르지 않고 일치율이 바뀐다 (우선순위: P2)

관리자가 평가 셋 라벨 화면에서 272쌍 중 한 쌍의 라벨을 고친다. 판사 버전 이력의 일치율은 다음에 열 때 고친 라벨로 다시 계산돼 있다. 판사(유료)는 호출되지 않는다.

**우선순위 이유**: 이 기능을 DB 로 옮기는 가장 큰 이유다. 지금은 라벨을 고칠 때마다 손으로 다시 세어 코드를 바꿔야 한다.

**독립 테스트 방법**: 라벨 한 쌍을 SAME 에서 DIFF 로 바꾼 뒤 판사 버전 이력의 v2 분자·분모가 그만큼 바뀌는지, 그동안 판사 호출이 0번인지 확인한다.

**인수 시나리오**:

1. **Given** v2 가 SAME 이라고 판정한 쌍의 사람 라벨이 SAME, **When** 관리자가 그 라벨을 DIFF 로 고친다, **Then** v2 의 같은 사건 분모가 1 줄고, 다른 사건 분모가 1 늘고, 그 쌍은 다른 사건에서 틀린 쌍으로 센다.
2. **Given** 라벨을 UNSURE 로 고침, **When** 다시 연다, **Then** 그 쌍은 두 분모에서 모두 빠진다.
3. **Given** 측정 뒤에 셋에 새로 들어온 쌍(그 측정에 판정 없음), **When** 일치율을 계산한다, **Then** 그 쌍은 분모에 넣지 않고 "측정에 없는 쌍 N개"로 따로 알린다.

---

### 사용자 스토리 3 - 새 판사 버전을 재면 결과가 DB 에 쌓인다 (우선순위: P3)

개발자가 판사 프롬프트나 모델을 바꿔 새 버전(v3)을 만들면, 기존처럼 평가 도구로 272쌍 일치율을 잰다(유료, 실행 전 승인). 결과는 마크다운 파일이 아니라 측정 기록과 쌍별 판정으로 DB 에 저장되고, 운영 DB 에도 들어가야 운영 채점이 그 버전을 쓸 수 있다.

**우선순위 이유**: 지금 v3 계획은 없다. 다음 버전 때 같은 흐름이 이어지게만 해 두면 된다.

**독립 테스트 방법**: 로컬 평가 사본에서 측정을 한 번 돌려(유료라 실제 실행은 사용자 승인 후) 측정 기록 1건과 쌍별 판정이 저장되는지 확인한다. 판사 호출 없이 확인하려면 판사를 가짜로 바꾼 테스트로 확인한다.

**인수 시나리오**:

1. **Given** 판사 버전 v3 이 코드에 있음, **When** 평가 도구로 일치율을 잰다, **Then** 측정 기록 1건과 판정한 쌍마다 쌍별 판정 1건이 저장된다.
2. **Given** 같은 버전을 두 번 쟀음, **When** 일치율을 계산한다, **Then** 가장 늦게 끝난 측정을 쓴다.
3. **Given** 측정 도중 판사 호출이 실패한 쌍이 있음, **When** 저장한다, **Then** 그 쌍은 호출 실패로 기록되고 일치율 분모에서 빠진다.
4. **Given** 운영 DB 에 측정 기록과 라벨이 없음, **When** 이 기능을 배포한다, **Then** v1·v2 측정 기록은 Flyway 시드 마이그레이션으로 들어가고, 272쌍 라벨은 사용자가 덤프(`backend/evaluation/datasets/pair_label_data_2026_11.sql`)를 DBeaver 로 배포 전에 넣는다(2026-11-25 결정 C — 측정은 한 번 만들면 고치지 않는 기록이라 시드, 라벨은 관리자 화면에서 고치는 데이터라 11-23 결정대로 덤프). 이후 새 버전 측정도 측정 기록은 시드 마이그레이션으로 운영에 넣는다.

---

### 예외 상황

- **현재 운영 판사 버전의 측정 기록이 DB 에 없으면?** 일일 채점은 지금처럼 그날을 채점하지 않고 warn 을 남긴다(돈이 나가지 않는 쪽). 다음 실행이 기록 없는 날을 다시 채점한다.
- **쌍별 판정이 없는 측정(v1)은?** 저장된 합계를 그대로 보이고, 라벨이 바뀌어도 다시 계산하지 않는다는 것을 화면에 알린다.
- **판사가 UNSURE·형식 실패로 답한 쌍은?** 지금 일치율 규칙과 같이 분모에서 빼고 따로 센다.
- **측정의 쌍이 셋에서 지워졌으면?** 그 쌍은 계산에 넣지 않는다(라벨이 없으니 정답이 없다).
- **측정 기록에 적힌 셋 이름의 라벨이 DB 에 하나도 없으면?** 그 측정은 계산할 수 없음으로 보이고, 일일 채점은 그 버전을 쓰지 않는다. **지금 운영 DB 가 바로 이 상태다** — 라벨과 측정 기록을 운영에 넣기 전에 배포하면 운영 일일 채점이 멈춘다. 배포 순서는 FR-013 을 따른다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 판사 일치율 측정마다 기록 하나를 저장해야 한다(MUST): 판사 버전, 모델, 평가 셋 이름, 측정을 마친 시각, 토큰 수와 추정 비용, 쌍별 판정이 있는지.
- **FR-002**: 측정마다 판정한 쌍의 판사 판정(SAME / DIFF / UNSURE / 형식 실패 / 호출 실패)을 쌍별로 저장해야 한다(MUST). 사람 라벨은 측정 기록에 복사하지 않고 계산 때 현재 라벨을 읽는다.
- **FR-003**: 버전의 일치율은 그 버전의 가장 늦게 끝난 측정의 쌍별 판정과 그 측정의 셋 이름에 해당하는 현재 사람 라벨로 계산해야 한다(MUST). 규칙은 지금과 같다 — 같은 사건 일치율 = 사람 SAME 중 판사 SAME, 다른 사건 일치율 = 사람 DIFF 중 판사 DIFF, 사람 UNSURE·판사 UNSURE·형식 실패·호출 실패는 분모에서 뺀다.
- **FR-004**: 쌍별 판정이 없는 측정(합계만 옮긴 v1)은 저장된 합계를 일치율로 써야 한다(MUST). 이 값은 라벨 변경에 따라 다시 계산되지 않는다는 표시를 함께 보여야 한다.
- **FR-005**: 코드의 일치율 상수를 없애야 한다(MUST). 판사 버전별 모델·지시문·단가는 코드에 남긴다 — 실제로 실행되는 판사는 코드이므로 DB 가 실행 중인 판사와 어긋나지 않게 한다.
- **FR-006**: 운영 일일 채점은 채점하는 순간 FR-003·FR-004 로 계산한 현재 판사 버전의 일치율을 그날 기록에 지금처럼 복사해야 한다(MUST). 이미 저장된 지난 날의 일치율은 바꾸지 않는다.
- **FR-007**: 현재 판사 버전의 측정 기록이 없으면 일일 채점은 판사를 부르지 않고 그날을 건너뛰어야 한다(MUST, 지금 동작 유지).
- **FR-008**: 관리자 대시보드의 판사 버전 이력은 FR-003·FR-004 의 값을 보여 줘야 한다(MUST). 측정에 없는 쌍이 셋에 있으면 그 수를 함께 보인다.
- **FR-009**: v2 의 2026-11-18 측정은 리포트(`backend/evaluation/reports/judge-agreement-2026-11-18-mini.md`)에서 쌍별 판정 225건을 복원해 넣어야 한다(MUST, 판사 재호출 없음). 리포트에 적힌 불일치 21쌍·판사 UNSURE 3쌍은 적힌 판정으로, 나머지는 그때 사람 라벨과 같은 판정으로 채운다. 복원 결과의 교차표가 리포트와 정확히 같아야 한다(SAME→SAME 127, SAME→DIFF 14, SAME→UNSURE 3, DIFF→DIFF 74, DIFF→SAME 7).
- **FR-010**: v1 의 2026-11-17 측정은 합계(124/142·77/80)만 쌍별 판정 없이 넣어야 한다(MUST).
- **FR-011**: 평가 도구의 판사 일치율 측정(`--eval.judge-agreement`, 유료)은 결과를 FR-001·FR-002 대로 접속한 DB 에 저장해야 한다(MUST). 실행 전 승인 원칙은 그대로다. 마크다운 리포트 파일은 더 내지 않고, 결과는 DB 에만 저장하며 콘솔에 요약(교차표·일치율·비용)만 로그로 남긴다(2026-11-25 결정 A). `--eval.judge-agreement` 와 함께 준 `--eval.report` 는 쓰지 않는다.
- **FR-012**: 측정 기록과 쌍별 판정은 저장 뒤 고치지 않는다(MUST). 다시 재면 새 측정 기록을 만든다.
- **FR-013**: 운영 일일 채점이 멈추지 않게, 일치율을 DB 에서 읽는 코드가 운영에서 돌기 전에 운영 DB 에 272쌍 라벨과 v2 측정 기록이 있어야 한다(MUST). v1·v2 측정 기록은 같은 배포의 Flyway 시드 마이그레이션으로 들어가므로 순서가 저절로 맞고, 라벨 덤프는 사용자가 배포 전에 넣는다. 라벨이 아직 없으면 FR-007 대로 그날 채점을 건너뛰고(비용 없음), 다음 실행(7일 안)이 다시 채점한다.

### 주요 엔티티

- **판사 측정**: 판사 버전 하나를 평가 셋 하나로 잰 기록. 버전, 모델, 셋 이름, 끝난 시각, 토큰·비용, 쌍별 판정 유무, (쌍별 판정이 없을 때만) 합계 일치율.
- **판사 쌍별 판정**: 측정 하나에서 알림 쌍 하나에 판사가 낸 판정. 사람 라벨은 담지 않는다.
- **사람 라벨**(기존, `evaluation_pair_label`): 셋 이름 + 알림 쌍 + 라벨. 일치율 계산의 정답.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 코드에 판사 일치율 숫자가 하나도 남지 않는다.
- **SC-002**: 이관 직후 판사 버전 이력의 v2·v1 일치율이 지금 화면 값과 같다(v2 127/141·74/81, v1 124/142·77/80).
- **SC-003**: 272쌍 중 한 쌍의 라벨을 바꾸면 판사 호출 0번으로 v2 일치율의 분자·분모가 그 변경만큼 바뀐다.
- **SC-004**: 이관 뒤 첫 운영 일일 채점이 기록 없이 건너뛰는 날 없이 v2 일치율과 함께 저장된다.

## 가정

- 272쌍 셋은 `evaluation_pair_label` 의 `cluster-eval-2026-11` 이고, 11-18 측정 때 라벨과 지금 DB 라벨은 같다(2026-11-24 JSON 과 DB 를 쌍·라벨 단위로 대조해 272쌍 모두 일치 확인).
- 측정은 지금처럼 평가 도구(`eval` 프로필)로 사람이 돌린다. 운영 화면에서 측정하는 버튼은 범위 밖이다.
- 판사 지시문·모델·단가는 코드(`ClusteringJudge`, `JudgeVersionCatalog`)에 남는다. 지시문 DB 이관은 범위 밖이다.
- 운영 DB 의 `evaluation_pair_label` 은 2026-11-25 현재 비어 있다(스키마는 V144 로 있음). 11-23 에 라벨 데이터는 Flyway 가 아니라 덤프로 사용자가 넣기로 했으나 운영에는 아직 넣지 않았다. 운영에서 일치율을 계산하려면 라벨과 측정 기록이 같은 DB 에 있어야 한다.
- 일일 채점 기록(`clustering_daily_score`)의 일치율 열과 저장 방식은 바꾸지 않는다.
