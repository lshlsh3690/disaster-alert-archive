> **Retroactive 명세 주석**: 본 명세는 이미 운영 중인 코드를 역분석한 as-built 문서다.
> 001~004와 동일하게, "구현 세부사항 없음" 계열 항목은 **의도적으로 완화**해 적용한다 —
> 이 문서의 목적 자체가 "현재 코드가 무엇을 하는가"를 file:line 근거와 함께 고정하는

## 콘텐츠 품질

- [x] 구현 세부사항(언어, 프레임워크, API)이 없음 — **의도적 예외**. Retroactive 명세라 모든 FR이 `file:line`을 인용한다. 001~004와 동일한 정책이며, 헌장 원칙 IV(정직한 문서화)가 요구하는 검증 가능성을 위해 필요하다.
- [x] 사용자 가치와 비즈니스 요구에 초점 — 4개 사용자 스토리 모두 "외국어 사용자가 재난 정보를 읽을 수 있다"는 가치로 우선순위를 매겼다.
- [x] 비기술 이해관계자를 위해 작성됨 — 각 스토리 서두는 평이한 한국어 서술이고, 코드 인용은 인수 시나리오·FR에 국한된다.
- [x] 모든 필수 섹션이 작성됨 — 사용자 시나리오/요구사항/성공 기준/가정 모두 작성.

## 요구사항 완결성

- [x] [NEEDS CLARIFICATION] 마커가 남아있지 않음 — 0건.
- [x] 요구사항이 테스트 가능하고 명확함 — FR-001~FR-017 전부 관측 가능한 동작이며 근거 라인이 붙어 있다.
- [x] 성공 기준이 측정 가능함 — SC-001은 테스트로 고정된 수치, SC-002~004는 "측정되지 않음"을 **사실로서** 명시(없는 SLA를 지어내지 않음).
- [ ] 성공 기준이 기술 구현과 무관함 — **미충족(의도적)**. SC-001·SC-003이 클래스명·빌드 설정을 인용한다. as-built 문서로서 검증 경로를 특정하는 것이 더 유용하다고 판단했다. 001~004도 동일.
- [x] 모든 인수 시나리오가 정의됨 — 스토리별 3~4개 Given/When/Then.
- [x] 예외 상황이 식별됨 — 알려진 결함 3건(동시성 500, 언어 매핑 이원화, VI/TH 지역명 영어 폴백) 포함 6건.
- [x] 범위가 명확히 한정됨 — FR-012가 법정동 번역을 명시적으로 제외(MUST NOT)하고, FR-017이 임베딩·클러스터링과의 경계를 긋는다. 이 명세의 주요 작성 동기.
- [x] 의존성과 가정이 식별됨 — OpenAI 자격증명 공유, DeepL 교체 이력, 사용자 생성 콘텐츠 미포함 전제 등 6개 항목.

## 기능 준비도

- [ ] 모든 기능 요구사항에 명확한 인수 기준이 있음 — **부분 충족**. FR-001~FR-012, FR-015~FR-016은 사용자 스토리의 Given/When/Then 시나리오와 대응한다. 반면 **FR-013**(모델·temperature), **FR-014**(프롬프트 표기 규칙), **FR-017**(임베딩과의 경계)은 Given/When/Then 매핑 없이 구현 라인 인용·성공 기준(SC-004)·경계 서술에만 의존한다. 셋 다 "관측 가능한 사용자 여정"이 아니라 시스템 내부 계약이라 as-built 문서에서는 시나리오화하기 어려웠다 — 검증은 `OpenAiTranslationClientRealApiTest`(FR-014 일부)와 코드 리딩(FR-013·FR-017)에 의존한다.
- [x] 사용자 시나리오가 주요 흐름을 다룸 — 사전 번역(P1) / 조회 시점 lazy(P2) / 이벤트 제목(P3) / 실패 폴백(P2) 4경로.
- [x] 성공 기준에 정의된 측정 가능한 결과를 충족함 — 현재 상태를 있는 그대로 기술.
- [ ] 구현 세부사항이 명세에 섞여있지 않음 — **미충족(의도적)**. 위 첫 항목과 같은 사유.
