# 기능 명세: 클러스터링용 임베딩 모델 선정

**기능 브랜치**: `feature/embedding-model-selection`

**생성일**: 2026-11-20

**상태**: Draft (2026-11-27 방향 전환 — 아래 절)

**입력**: 사용자 설명: "임베딩 모델 선정. 우리 클러스터링 파이프라인에 맞는 임베딩 모델을 찾는다. 판단 기준은 클러스터링 성능 향상과 비용의 트레이드오프. 현재는 OpenAI text-embedding-3-small(1536차원)이고, 새 알림마다 1회 임베딩해 같은 시군구 후보 이벤트와 코사인 거리 0.15 이하면 병합한다(사고성 유형은 경계선 거리에서 LLM 폴백). 2026-11-20 확인: 호우 튜닝 뒤 272쌍 평가(reports/2026-11_2026-11-12-rain72.md)에서 남은 오류는 과소병합 17쌍(화재 8 등)·과병합 11쌍(화재 6 등)이고, 화재는 과병합 쌍 거리 0.118~0.300와 과소병합 쌍 거리 0.203~0.483이 겹쳐 임계값만으로는 못 가른다. 성능은 사람 라벨 272쌍으로 잰다 — LLM 판사 점수로 고르지 않는다. 첫 단계는 운영을 건드리지 않고 272쌍 알림만 후보 모델로 다시 임베딩해 보는 싼 실험. 비용은 임베딩 단가×운영 알림 수와 재클러스터링 비용을 함께 본다. 1536 으로 줄여 받을 수 있는 모델이면 스키마 변경 없이 바꿀 수 있다. 모델을 바꾸면 임계값 0.15 재튜닝이 필요하다. 유료 호출은 명시 승인 후에만. 하지 않는 것: 운영 모델 교체(선정·근거까지), 클러스터링 규칙 변경."

## 2026-11-27 방향 전환 (사용자 결정)

1단계(쌍 거리)로 후보를 거른 뒤 최대 2개만 재클러스터링하던 흐름을 바꿨다. 1단계 쌍 거리 실험은 코드·결과·문서를 모두 지웠다(2026-11-27 사용자 결정, git 이력: 측정 코드 fd67f476·67a78d85, 결과 77611dda). 거기서 본 모델별 거리 분포만 research R10 에 수치로 남긴다.

- **후보 4개와 기준선을 모두 실제 재클러스터링한다(총 5회).** 쌍 거리는 대리 지표라 실제 파이프라인(가장 가까운 알림 비교, 연쇄 병합, LLM 폴백, 후보 검색)의 효과를 못 본다. 기준선(`3small`)도 같은 코드·같은 방식으로 한 번 돌려, 모델만 다른 비교를 만들고 흔들림을 잰다.
- **거리 기준은 모든 모델에 운영 값 그대로(0.15 바로 병합, 0.40 LLM 상한, 동물 경로 하한 0.6).** 모델별로 기준을 맞추는 방법(라벨로 맞추기, 라벨로 훑기, 라벨 없는 분포로 맞추기)은 쓰지 않는다. 그래서 병합 거리 설정화(옛 T007·T008)는 필요 없고, 기준을 라벨로 정하지 않으니 같은 라벨로 채점해도 점수가 부풀지 않는다. 대가: 거리 눈금이 운영 모델과 크게 다른 모델(예: e5 는 다른 사건 거리 중앙값 0.062)은 기준이 맞지 않아 불리하게 나올 수 있고, 결과를 읽을 때 research R10 의 거리 분포로 그 이유를 밝힌다.
- **모델별 임베딩은 별도 로컬 DB 에 행 단위로 보관해 재사용한다.** 평가 사본 알림 62,554건 × 모델. `3small` 은 평가 사본에 저장된 임베딩을 쓴다.
- **재클러스터링 결과는 모델마다 평가 사본을 따로 둔다**(`disaster_alert_eval_e_<별칭>`), 틀린 쌍을 나중에 다시 들여다보기 위해.
- **호출은 로컬 LiteLLM 프록시를 거치고, 실행마다 가상 키를 하나씩 쓴다**(`infra/llm-usage/`). 채우기·LLM 폴백 비용이 실행별로 기록되고, 키마다 허용 모델과 예산 상한을 건다.

## 배경

새 재난문자는 들어올 때마다 임베딩(문장을 숫자 벡터로 바꾼 것)이 만들어진다. 클러스터링은 같은 시군구 후보 이벤트마다 **그 이벤트 알림들 중 새 알림과 가장 가까운 거리**를 보고, 0.15 이하이면 그 이벤트에 붙인다. 사고성 유형은 0.15~0.40 구간에서 LLM 에게 한 번 더 묻는다. 지속형(폭염·대설 등)과 지역 한정 유형(산불·산사태·홍수·호우)은 유형+시군구 키로 묶어 임베딩 거리를 보지 않는다. 따라서 임베딩 모델이 성능을 좌우하는 곳은 **나머지 유형(화재·교통·수도·정전 등)의 임베딩 경로와 LLM 폴백 구간**이다.

호우 튜닝 뒤(2026-11-12, 272쌍) 점수는 90.2점이다(당시 대표 지표 F1. 2026-11-24 부터 대표 지표는 균형 정확도, specs/013. 맞게 묶은 비율: 묶은 140쌍 중 129쌍, 빠짐없이 묶은 비율: 같은 사건 146쌍 중 129쌍). 남은 오류 28쌍 중 화재가 14쌍이다. 화재는 같은 사건인데 거리가 먼 쌍(0.203~0.483)과 다른 사건인데 거리가 가까운 쌍(0.118~0.300)이 겹친다. 지금 모델로는 임계값을 어디에 두어도 한쪽이 틀린다. 더 나은 모델이 이 겹침을 줄이는지가 이 기능의 질문이다.

**비용 규모(추정, plan 에서 단가 확인)**: 272쌍 알림은 서로 다른 544건이고 본문 평균은 76자다. 알림 1건을 약 100토큰으로 잡으면 운영 알림 6만여 건 재임베딩은 약 600만 토큰이다. 지금 모델 단가로 약 $0.1, 더 큰 OpenAI 모델 단가로도 $1 안팎이다. 따라서 API 임베딩 모델끼리는 **단가 차이가 거의 무시할 만하다**. 비용 쪽에서 실제로 저울에 오르는 것은 전환 부담이다. 재임베딩 중 테이블 갱신으로 약 100초 배포 지연이 생기고, 거리 기반 임계값을 다시 튜닝해야 하며, 재클러스터링 때 LLM 폴백 호출이 든다(호우 튜닝 때 980회 약 $0.3). 직접 운영하는 모델을 후보에 넣으면 서버 자원과 운영 부담도 더해진다.

## 사용자 시나리오 및 테스트 *(필수)*

### 사용자 스토리 2 - 모든 후보로 실제 클러스터링을 다시 돌려 점수를 비교한다 (우선순위: P2)

개발자는 후보 4개마다 평가 사본 전체를 그 모델로 다시 임베딩하고(보관 DB 에 있으면 재사용), 운영과 같은 거리 기준으로 재클러스터링한다. 기준선(`3small`)도 저장 임베딩으로 같은 방식으로 한 번 재클러스터링한다(2026-11-27). 그리고 272쌍으로 평가해 지금 리포트와 같은 형식(맞게 묶은 비율·빠짐없이 묶은 비율·점수, 고쳐진 쌍·새로 틀린 쌍)으로 기준선과 비교한다.

**우선순위 이유**: 쌍 거리는 클러스터링 결과의 대리 지표일 뿐이다. 실제로는 이벤트가 커지며 가장 가까운 알림이 바뀌고, LLM 폴백 구간도 움직인다. 전환 여부는 이 점수로 판단해야 한다.

**독립 테스트 방법**: 같은 절차를 기준선 모델로 한 번 돌려 지금 점수(90.2점, 같은 라벨 기준)가 재현되는지 먼저 확인한다. 재현되지 않으면 후보 비교를 하지 않는다.

**인수 시나리오**:

1. **Given** 후보 1개와 운영과 같은 거리 기준, **When** 평가 사본을 재임베딩(또는 보관 DB 에서 가져오기)·재클러스터링하고 평가하면, **Then** 기준선과 같은 라벨·같은 LLM 폴백 설정으로 잰 두 비율과 점수, 고쳐진 쌍·새로 틀린 쌍 목록이 나온다.
2. **Given** 실행 전, **Then** 재임베딩(사본 알림 전체)과 재클러스터링 LLM 폴백의 예상 비용이 보이고, 사용자 승인 전에는 호출이 0건이다. 실행 뒤에는 그 실행 키의 실제 비용이 프록시 기록에 남는다.
3. **Given** 결과, **Then** 후보의 점수 차가 같은 설정으로 기준선을 두 번 돌렸을 때 생기는 흔들림보다 작으면 "차이 없음"으로 적는다.

---

### 사용자 스토리 3 - 성능과 비용을 한 표로 보고 선정한다 (우선순위: P3)

개발자는 모델마다 재클러스터링 점수, 1회 전환 비용(재임베딩·재튜닝·재클러스터링·배포 지연), 매일 드는 비용, 스키마 변경 여부, 운영 부담을 한 표로 보고 모델을 고른다. 고른 이유와 버린 후보의 이유는 결정 기록으로 남긴다. 운영 모델 교체는 이 기능에서 하지 않는다.

**우선순위 이유**: 선정의 산출물이자, 면접·포트폴리오에서 "왜 이 모델인가"에 답하는 근거다. "바꾸지 않는다"도 정당한 결론이다.

**독립 테스트 방법**: 표의 비용 숫자가 단가 × 토큰 수로 다시 계산되는지, 점수가 리포트 파일의 숫자와 같은지 확인한다.

**인수 시나리오**:

1. **Given** 실험 결과, **When** 표를 만들면, **Then** 후보마다 성능(N쌍 중 M쌍 또는 점수), 1회 비용, 월 비용, 전환 작업 목록이 한 줄에 있다.
2. **Given** 어느 후보도 기준선보다 낫지 않으면, **Then** 결론은 "지금 모델 유지"이고, 남은 화재 오류는 임베딩으로는 풀리지 않는다는 근거(쌍 목록)를 함께 남긴다.
3. **Given** 선정이 끝나면, **Then** 운영 설정·운영 DB 는 그대로다.

### 예외 상황

- 채우기가 일부 알림에서 실패하면 그 수를 보이고, 빈 임베딩이 남은 사본으로는 재클러스터링하지 않는다(`count(*)`·`count(embedding)` 확인).
- 같은 입력에 임베딩이 조금씩 다르게 나오는 모델이면 기준선을 두 번 재서 흔들림 크기를 밝힌다.
- 사람 라벨이 모르겠음인 쌍은 어느 계산에도 넣지 않는다.
- 평가 사본에 없는 알림이 있으면 실험 전에 그 수를 보이고 그 쌍을 뺀다.
- (2026-11-27 해소) 거리 기준을 라벨로 맞추지 않으므로(운영 값 고정) 같은 272쌍으로 채점해도 점수가 부풀지 않는다. 2026-05 B-cubed 정답 점수는 리포트에 함께 붙인다(라벨 기준 시점 차이를 밝힘).
- 가상 키의 예산 상한에 걸려 실행이 중간에 멈추면, 그 사본은 반쯤 채워진 상태라 버리고 처음부터 다시 돌린다.
- 공개 모델(직접 운영)은 그 모델의 임베딩 속도도 잰다. 수집 루프 안에서 동기로 돌기 때문에, 알림 1건당 시간이 수집 주기(1분)를 위협하면 실격이다.

## 요구사항 *(필수)*

### 기능 요구사항

**후보와 범위**

- **FR-001**: 후보 모델은 OpenAI 임베딩 모델과 Hugging Face 공개 모델(예: BAAI 계열)이다(MUST, 2026-11-20 사용자 결정). 2026-11-20 확정 후보(5개):

  | 모델 | 구분 | 파라미터 | 차원 | 라이선스 |
  |---|---|---|---|---|
  | `text-embedding-3-small` | 기준선(지금 모델), OpenAI API | 비공개 | 1536 | 유료 API |
  | `text-embedding-3-large` | OpenAI API | 비공개 | 3072 → 1536 으로 줄여 받기 | 유료 API |
  | `Qwen/Qwen3-Embedding-0.6B` | 공개 모델 | 약 6.0억 | 1024 | Apache-2.0 |
  | `intfloat/multilingual-e5-large-instruct` | 공개 모델 | 약 5.6억 | 1024 | MIT |
  | `dragonkue/BGE-m3-ko` | 공개 모델(bge-m3 한국어 추가 학습) | 약 5.7억 | 1024 | Apache-2.0 |

  공개 모델은 MTEB(kor, v2) 리더보드에서 10억 파라미터 이하·상업 이용 가능 라이선스로 거른 뒤, 같은 사건 판정에 가까운 NLI·STS·PawsX 점수로 골랐다(선정 근거와 점수 원본: [candidate-selection.md](candidate-selection.md), [data/](data/)). 사용자 결정으로 뺀 것: `BAAI/bge-m3` 원본. 조건 때문에 뺀 것: `jina-embeddings-v5` 계열(CC-BY-NC 비상업), 10억 파라미터 초과 모델. 리더보드에서 10억 이하 모델의 PawsX(단어가 겹치는데 뜻이 다른 쌍)는 모두 48~53점이었다(무작위 기준선 44.7점). 그래서 같은 템플릿에 번지만 다른 화재 과병합은 모델을 바꿔도 줄지 않을 수 있다는 것을 미리 적어 둔다. 헌법 "기술 스택 제약"은 임베딩을 "Spring AI 경유 OpenAI 정식 API"로 정해 두었으므로, 공개 모델이 선정되면 운영 교체 전에 헌법 개정이 필요하다(이 기능은 선정까지라 개정하지 않는다).
- **FR-001a**: 공개 모델 후보마다 운영 서버(맥북)에서 돌릴 수 있는지(메모리·속도)와 라이선스를 기록해야 한다(MUST). 알림 1건 임베딩 시간이 수집 주기를 위협하면 실격이다(예외 상황 참고).
- **FR-002**: 지금 모델(`text-embedding-3-small`, 1536차원)은 모든 비교에 기준선으로 들어가야 한다(MUST).
- **FR-003**: 후보마다 1536차원 이하로 받을 수 있는지, 아니면 저장 구조를 바꿔야 하는지 기록해야 한다(MUST).

**2단계: 재클러스터링 비교 (스토리 2)**

- **FR-007**: 지표는 두 비율(맞게 묶은 비율·빠짐없이 묶은 비율)·점수(균형 정확도)·"N쌍 중 M쌍"으로 한정한다(MUST). 거리 분포 곡선 면적이나 여러 임계값을 훑는 표 같은 지표는 쓰지 않는다(2026-10-19 결정: 이해 가능한 지표만).
- **FR-008**: 후보 4개(`3large`·`qwen3_06b`·`e5_large_instruct`·`bge_m3_ko`)를 모두 재클러스터링한다(MUST, 2026-11-27). 후보를 거르지 않는다.
- **FR-009**: 2단계는 평가 사본의 복제본에서만 하고, 기준선(`3small`, 저장 임베딩)도 같은 절차로 한 번 재클러스터링해야 한다(MUST). 기준선 재실행 점수와 v6 기존 배정 점수의 차이를 흔들림으로 적는다.
- **FR-010**: 거리에 기대는 설정값은 모든 모델에 운영 값 그대로 쓴다(MUST, 2026-11-27): 바로 병합 0.15(코드에 고정), LLM 폴백 상한 0.40, 동물 경로 유사도 하한 0.6. 클러스터링 규칙(경로·키·시간 창)과 운영 코드는 바꾸지 않는다(MUST).
- **FR-011**: 결과는 지금 평가 리포트와 같은 형식(맞게 묶은 비율·빠짐없이 묶은 비율·점수, 고쳐진 쌍·새로 틀린 쌍)이어야 하고, LLM 폴백을 켠 상태로 잰다(MUST).
- **FR-012**: 점수 차가 기준선 재실행의 흔들림보다 작으면 "차이 없음"으로 판정해야 한다(MUST).

**선정 (스토리 3)**

- **FR-013**: 후보마다 성능, 1회 전환 비용(재임베딩 비용, 배포 지연, 임계값 재튜닝 작업, 재클러스터링 LLM 비용), 매일 비용, 스키마 변경 여부, 운영 부담을 한 표로 남겨야 한다(MUST).
- **FR-014**: 성능과 비용을 맞바꾸는 판정은 선정 표(FR-013)를 보고 사용자가 정한다(MUST). 2026-11-27 사용자가 "성능 측정 기준부터 마련해야 한다"고 해 판정 기준을 실행 전에 정하기로 했다. **확정(2026-11-27, 결과를 보기 전)**: 기준선 대비 과병합·과소병합 **둘 다 늘지 않고 하나라도 줄어야 "나아짐"**(맞바꿈은 나아짐 아님), 줄어든 차이는 흔들림(FR-012)보다 커야 하고, 화재 쌍만 따로 세어 과병합·과소병합 중 하나라도 기준선보다 늘면 탈락, 균형 정확도는 통과한 모델들의 순위에만 쓴다. 통과한 모델이 없으면 "지금 모델 유지". 상세와 이유는 research R10, 결정 기록(FR-015)은 이 기준을 따른다.
- **FR-015**: 선정 결과와 근거(버린 후보 포함)를 결정 기록으로 남겨야 한다(MUST). "지금 모델 유지"도 결론이 될 수 있다.

**원칙**

- **FR-016**: 모든 유료 호출(후보 임베딩, 평가 사본 재임베딩, 재클러스터링 LLM 폴백)은 예상 비용을 먼저 보이고 사용자의 명시적 승인 뒤에만 실행해야 한다(MUST).
- **FR-017**: 성능 판단은 사람 라벨로만 한다(MUST). LLM 판사 점수는 선정 근거로 쓰지 않는다.
- **FR-018**: 이 기능은 운영 임베딩 모델·운영 데이터·클러스터링 규칙을 바꾸지 않아야 한다(MUST). 교체는 선정 뒤 별도 작업이다.

**재사용과 사용량 기록 (2026-11-27)**

- **FR-019**: 모델별 임베딩(평가 사본 알림 전체)은 별도 로컬 DB 에 (알림, 모델) 한 행씩 보관하고, 같은 모델로 다시 재클러스터링할 때는 API 를 다시 부르지 않고 보관본을 쓴다(MUST). 운영 스키마(Flyway)에는 넣지 않는다.
- **FR-020**: 채우기·재클러스터링의 모든 모델 호출은 로컬 LiteLLM 프록시를 거치고, 실행(기준선 1 + 후보 4)마다 가상 키 하나를 쓴다(MUST). 키마다 허용 모델(그 실행의 임베딩 모델 + LLM 폴백 `gpt-4o-mini`)과 예산 상한을 건다. 결정 기록의 실행별 비용은 이 키의 기록에서 가져온다.

### 주요 엔티티 *(데이터가 관련된 경우 포함)*

- **후보 모델**: 이름, 제공자, 받을 수 있는 차원, 단가(또는 직접 운영 비용), 1536차원 이하 가능 여부.
- **재클러스터링 결과**: 모델(기준선 포함 5개) × 평가 리포트 1개(두 비율·점수·쌍 목록), 평가 사본 이름, 가상 키 별칭과 실제 비용.
- **임베딩 보관본**: (알림, 모델) 한 행 — 차원, 벡터, 만든 시각. 별도 로컬 DB.
- **선정 기록**: 후보별 성능·비용 표, 판정, 근거.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-003**: 기준선 재실행 점수와 v6 기존 배정 점수의 차이(흔들림)가 리포트에 있고, 후보 점수 차는 이 흔들림과 나란히 적힌다.
- **SC-007**: 실행 5개의 실제 비용(임베딩 채우기·LLM 폴백)이 가상 키별로 프록시 기록에 있고, 결정 기록의 비용 숫자와 같다.
- **SC-004**: 선정 표의 모든 비용 숫자가 단가 × 토큰 수로 다시 계산되고, 모든 성능 숫자가 리포트 파일에 있다.
- **SC-005**: 사용자 승인 없이 일어난 유료 호출이 0건이다.
- **SC-006**: 결정 기록만 읽고도 "왜 이 모델(또는 왜 유지)인가"를 숫자와 쌍 예시로 설명할 수 있다.

## 가정

- 성능 기준 셋은 평가 셋 `cluster-eval-2026-11`(272쌍, DB `evaluation_pair_label`)이다. 라벨은 이 기능에서 바꾸지 않는다. 2026-11-17 라벨 재확인 뒤의 라벨을 쓴다. 그래서 2단계 기준선 점수는 11-12 의 90.2점과 조금 다를 수 있고, 먼저 지금 라벨로 기준선을 다시 잰다.
- 평가 사본은 지금 쓰는 사본(호우 튜닝이 반영된 것)을 쓰고, 2단계용 사본은 그 복제본에서 만든다. 기준선 사본을 덮어쓰지 않는다.
- 임베딩 입력은 지금과 같이 알림 본문 그대로다. 본문 정규화·요약 같은 입력 가공은 하지 않는다(2026-10-11 결정: 본문 정규화 계층은 만들지 않음).
- 단가는 plan 에서 각 제공자의 공개 가격표로 확인하고 확인 날짜를 적는다. 배경의 비용 규모는 알림당 100토큰 가정의 추정이다.
- 운영 알림 수는 평가 사본 알림 수(62,554건)로 추정한다. 비용 규모가 작아 운영 DB 를 따로 조회하지 않는다.
- 재임베딩 때 `disaster_alert` 대량 갱신은 건당 약 1.6ms(6만 건 약 100초)가 든다(2026-11-19 실측). 임베딩 컬럼 분리는 하지 않는다.
- LLM 판사·일일 채점은 이 기능과 무관하다. 모델을 바꿔도 판사 입력에는 임베딩이 들어가지 않는다.
