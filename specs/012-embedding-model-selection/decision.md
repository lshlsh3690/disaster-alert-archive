# 결정 기록: 클러스터링용 임베딩 모델 선정

**명세**: [spec.md](spec.md) | **모델 비교 기준**: [research.md](research.md) R10 | **실행 절차**: [quickstart.md](quickstart.md)
**작성**: 2026-11-28 | **실험**: 2026-11-27 (평가 사본 `disaster_alert_eval_v6`, 알림 62,554건 중 임베딩 60,382건)

## 결론

**`Qwen/Qwen3-Embedding-0.6B`(qwen3_06b)를 고른다(사용자 판정, 2026-11-27).** 운영 교체는 이 기능에서 하지 않고 새 명세로 연다.

### 1. 후보를 어떻게 골랐나

Hugging Face 의 MTEB 리더보드(Benchmarks → Korean, MTEB(kor, v2))에서 과제별 점수 CSV(모델 271개 × 과제 20개, 2026-11-20)를 받아 후보를 추렸다([candidate-selection.md](candidate-selection.md)). 리더보드 점수로 모델을 정한 것이 아니라, 우리 데이터로 시험해 볼 후보를 고른 것이다.

1. **크기**: 10억 파라미터 이하. 운영 맥북에서 Postgres·Redis·앱과 함께 돌고, 새 알림마다 수집 루프 안에서 임베딩하기 때문이다.
2. **라이선스**: 상업 이용 가능(MIT·Apache-2.0). NLI·STS 가 가장 좋던 `jina-embeddings-v5` 는 비상업 라이선스라 뺐다.
3. **한국어**: 다국어 또는 한국어 추가 학습 모델.
4. **과제 점수**: 평균 점수가 아니라 우리 일에 가까운 과제만 봤다.
   - NLI: 말이 달라도 뜻이 이어지는가. 과소병합과 관련된다.
   - STS: 거리 순서가 사람이 느끼는 비슷함과 맞는가. 거리 기준값 하나로 가르는 방식과 관련된다.
   - PawsX: 단어가 거의 같은데 뜻이 다른 쌍을 가르는가. 같은 문구 틀에 번지만 다른 화재, 즉 과병합과 관련된다.

| 구분 | 모델 | 차원 | 고른 이유 |
|---|---|---|---|
| 기준선 | `text-embedding-3-small` | 1536 | 지금 운영 모델 |
| 후보 | `text-embedding-3-large` | 1536 | 같은 회사 상위 모델, 1536 으로 받으면 스키마 변경 없음 |
| 후보 | `Qwen/Qwen3-Embedding-0.6B` | 1024 | 조건 통과 모델 중 NLI·PawsX 최고 |
| 후보 | `intfloat/multilingual-e5-large-instruct` | 1024 | NLI·STS 균형 |
| 후보 | `dragonkue/BGE-m3-ko` | 1024 | 한국어 추가 학습 모델 중 STS 최고 |

실험 전에 적어 둔 예상: 10억 이하 모델의 PawsX 는 모두 48~53점이다. 무작위 인코더가 44.7점이라, 이 크기에서는 번지만 다른 화재 쌍을 거리로 거의 가르지 못한다. 그래서 화재 과병합은 모델을 바꿔도 줄지 않을 수 있다고 봤다. 실제로 번지 다른 화재 과병합 7쌍이 다섯 모델 모두에서 나왔다(부록 A).

### 2. 어떻게 비교했나

1. **실제 클러스터링을 처음부터 다시 돌렸다.** 평가 사본(알림 62,554건, 2023-09 ~ 2026-10)의 임베딩을 모델마다 새로 채우고(60,382건), 운영과 같은 코드로 이벤트를 전부 다시 묶었다. 기준선도 같은 방식으로 다시 돌렸다.
2. **거리 기준은 운영 값 그대로 썼다.** 바로 병합 0.15, LLM 판정 상한 0.40, 동물 0.6 을 다섯 모델에 똑같이 적용했다. 모델에 맞춰 바꾸지 않았다.
3. **사람 라벨로 채점했다.** 라벨은 [CLUSTERING_CRITERIA.md](../001-event-clustering-pipeline/CLUSTERING_CRITERIA.md) 1절 기준으로 매긴 272쌍이다. 유형이 화재인 78쌍을 뺀 나머지(같은 사건 104쌍·다른 사건 42쌍)에서 과소병합·과병합 수를 기준선과 비교했다.
4. **"나아짐"의 조건**: 과소병합·과병합이 둘 다 늘지 않고, 하나라도 흔들림(같은 모델을 두 번 돌렸을 때의 차이, 1쌍)보다 크게 줄어야 한다. 한쪽이 줄고 다른 쪽이 늘면 "나아짐"이 아니다.
5. 보조로 2026-05 알림 230건을 사건별로 묶어 둔 정답(B-cubed)으로 알림 단위 점수를 냈다.
6. 모든 모델 호출은 LiteLLM 프록시를 거쳐 실행마다 가상 키 하나로 비용을 나눠 기록했다.

### 4. 왜 qwen 인가

- **성능은 qwen 과 3large 가 같다.** 틀린 쌍 수가 똑같다(과소병합 4, 과병합 4).
- **비용은 qwen 이 무료다.** 3large 는 평가 사본 60,382건 임베딩에 $0.70 이 들었다(운영으로 옮기면 한 번 약 $0.8, 매달 약 $0.02 추정). qwen 은 $0 이다.
- **운영 맥북에서 돌릴 수 있다.** Docker CPU 방식(메모리 5GB 상한)으로 알림 1건을 약 0.7초에 임베딩한다. 수집 루프는 새 알림을 한 건씩 차례로 처리하므로, 임베딩만으로 한 주기 1분을 넘기려면 약 86건이 한꺼번에 들어와야 한다. 평가 사본(2023-09 ~ 2026-10)에서 같은 1분에 나온 알림은 최대 6건이었다(99% 는 3건 이하). 맥 GPU 는 Docker 안에서 쓸 수 없고, Docker 밖에서 띄우면 메모리 상한이 없어 운영이 멈출 수 있어 쓰지 않는다(아래 "맥북 측정").

| 다른 사건을 묶은 쌍 (과병합, 42쌍 중) | 4 | 4 (그대로) |

- 고친 4쌍은 단수·정전처럼 한 사건이 단계별로 문자를 내는 경우다(복구 완료 ↔ 급수 지연, 발전기 정전 ↔ 복구 지연 등).
- 한계: 개선 폭은 4쌍으로, 흔들림(1쌍)보다는 크지만 272쌍 안의 결과라 운영 전체의 개선 폭으로 넓혀 말하지 않는다. 쌍 라벨은 두 문자만 보고 붙여서 단계별로 이어지는 사건의 판단이 흔들릴 수 있다(아래 "측정의 한계").
- 운영에 옮기려면 헌법 기술 스택 개정, `vector(1024)` 마이그레이션, 운영 알림 전체 다시 임베딩(약 13시간)이 필요하다(아래 "운영에 옮길 때").
- 실험 전체 비용은 약 $0.90 이고, 후보 임베딩은 로컬 DB `embedding_store` 에 보관해 다시 돌릴 때 API 를 부르지 않는다.

e5 는 거리 눈금이 좁다. 다른 사건끼리의 거리 중앙값이 0.062 로 3small(0.387)의 6분의 1이다(research R10, 2026-11-27 137쌍 측정). 그래서 운영 값 0.15 로는 다른 사건도 대부분 바로 병합되고, LLM 판정 호출도 12회뿐이었다(다른 모델 889~1,015회). 거리 기준을 모델마다 맞추지 않기로 한 A 방식의 대가가 그대로 나온 결과다.

## 라벨 수정 (2026-11-27, 사용자 결정)

## 측정의 한계: 쌍 라벨은 두 문자만 보고 붙였다

클러스터링은 새 알림을 이벤트 안 알림 중 **가장 가까운 한 건**과 비교한다([DisasterEventRepository.java](../../backend/src/main/java/com/disaster/alert/alertapi/domain/event/repository/DisasterEventRepository.java) `MIN(embedding <=> 새 임베딩)`). 그래서 두 문자가 서로 달라도 사이 알림을 타고 같은 이벤트에 들어간다. 그런데 쌍 라벨은 라벨을 붙인 사람이 두 문자만 보고 정했다.

- 각 문자가 장소·번지·시각으로 사건을 스스로 밝히는 쌍(화재 대부분)은 두 문자만으로 판단된다. 부록 A 의 화재 과병합 쌍이 여기 속한다.
- 한 사건이 단계별로 문자를 내는 유형(단수·정전처럼 발생 → 복구 → 여파 → 정상화)은 두 문자만으로 판단이 안 될 수 있다. 맞게 묶은 것을 과병합으로 셀 수도, 그 반대일 수도 있다.
- qwen·3large 가 고친 4쌍이 바로 이 두 번째 종류(수도·정전)라, 개선 폭은 라벨만큼 확실하지 않다. 같은 한계는 2026-11-11 호우·산불 50쌍에서 앞뒤 문자와 함께 다시 매겨 다룬 적이 있고(30쌍 변경), 수도·정전 유형은 그때 다시 보지 않았다.
- 알림 단위 점수(2026-05 B-cubed)는 사람이 알림을 사건별로 묶어 둔 정답이라 흐름을 본 정답이다. 이 점수에서도 qwen(95.8)·3large(95.5)가 기준선(93.7)보다 높다. 다만 2026-05 알림 230건 범위이고, 그 정답의 기준 시점(2026-11-10)이 272쌍(2026-11-13)과 다르다.

## 운영에서 기대하는 변화와 관측 방법

교체 뒤 아래를 본다. 예상치는 평가 사본(2023-09 ~ 2026-10, 60,382건)에서 기준선 사본과 qwen 사본을 비교한 값이라 운영에서 같은 크기로 나온다는 보장은 없다. **교체 전 4주를 같은 쿼리로 먼저 기록해 기준점으로 삼는다.** 운영 쿼리는 맥북 `disaster-postgres` 에 읽기 전용(`BEGIN TRANSACTION READ ONLY`)으로 돌린다.

### 기대하는 변화

| 변화 | 평가 사본 예상 (3small → qwen) | 이유 |
|---|---|---|

운영 규모가 작다. 최근 12개월 사건 알림은 한 달에 수도 약 12.5건, 정전 약 7.9건, 화재 약 60.8건이다. 그래서 수도·정전 변화는 하루 단위로는 보이지 않고, **최소 3개월치를 모아야** 차이를 말할 수 있다.

### 관측 방법

**1. 유형별 쪼개짐 (월 1회, 무료)** — 수도·정전의 "알림 1건짜리 이벤트 비율"이 내려가고 "이벤트당 알림 수"가 올라가면 기대대로다.

```sql
WITH e AS (
  SELECT event_id, min(disaster_type) AS t, count(*) AS n, min(created_at) AS first_at
  FROM disaster_alert WHERE event_id IS NOT NULL GROUP BY event_id)
SELECT date_trunc('month', first_at) AS month, t,
       count(*) AS events, sum((n = 1)::int) AS single, round(avg(n), 2) AS avg_size
FROM e WHERE t IN ('수도', '정전', '화재')
GROUP BY 1, 2 ORDER BY 1, 2;
```

**2. 일일 채점 (`clustering_daily_score`, 이미 매일 01:00 에 돈다)** — `missed`(과소병합)가 줄고 `over_merged`(과병합)는 그대로인지 본다. 판사 버전(`judge_version`)이 같은 기간끼리만 비교하고, 판사 일치율(`agreement_*`)을 함께 적는다. 하루 쌍 수가 적어 주·월로 합친다.

```sql
SELECT date_trunc('week', score_date) AS week, judge_version,
       sum(pair_count) AS pairs, sum(correctly_merged) AS ok, sum(missed) AS missed, sum(over_merged) AS over_merged
FROM clustering_daily_score GROUP BY 1, 2 ORDER BY 1;
```

화재 과병합은 `clustering_daily_score_pair` 에서 시스템이 같은 이벤트로 묶었는데 판사가 다르다고 한 쌍을 뽑아 원문을 읽는다(부록 A 와 같은 모양인지).

**3. 병합 방식 분포 (월 1회, 무료)** — `EMBEDDING` 비중이 오르고 `LLM_FALLBACK`·`SEED` 비중이 내리면 기대대로다.

```sql
SELECT date_trunc('month', event_added_at) AS month, event_merge_method, count(*)
FROM disaster_alert WHERE event_merge_method IS NOT NULL
GROUP BY 1, 2 ORDER BY 1, 3 DESC;
```

**4. 처리 시간** — 백엔드 로그(LogTrace)의 `EventClusteringService.clusterNewAlert(..) time=…ms` 를 교체 전후로 비교한다. 임베딩과 LLM 판정 시간이 함께 들어 있다. 매분 수집 한 번에 처리한 시간이 1분에 가까워지면 문제다(호우 때처럼 알림이 몰리는 날을 따로 본다).

**5. 안정성** — 임베딩 장애는 이제 TEI 컨테이너에서 난다.
- `clustering_daily_check` 의 `no_embedding_count`·`unassigned_count`: 늘면 TEI 호출이 실패한 것이다(README "운영 일일 구조 검사").
- `docker inspect disaster-tei-qwen3 --format '{{.State.OOMKilled}} {{.RestartCount}}'`, `docker stats`: 메모리 상한 5GB 근처까지 가거나 재시작이 생기는지.
- 백엔드 로그의 임베딩 호출 예외.

**6. 비용** — 운영 호출은 LiteLLM 을 거치지 않으므로 OpenAI 사용량 화면에서 임베딩 줄이 0이 되는지, `gpt-4o-mini` 사용량이 조금 주는지 본다.

**판단**: 3개월 뒤 1·2·3 이 예상 방향이고 5 에 문제가 없으면 교체가 기대대로 된 것이다. 2 에서 과병합이 늘거나 5 에서 장애가 반복되면, 옛 임베딩으로 돌아갈지 정한다. 돌아가려면 다시 1536차원 재임베딩이 필요하므로, 교체 때 옛 `embedding` 값을 백업해 둔다.
